### RM Store — Stock Adjustment: Minus breakdown showed coils from other MRNs

- **Problem:** Minus (-) with a specific MRN UID (e.g. `4041_1`) listed coils from other MRNs (e.g. `4272_1`, `4273_3`). The header stayed correct; only the coil list was wrong.
- **Cause:** When the selected MRN had no active coils, `findActiveCoilsForMinus` fell back to an item-code-only query and returned every active coil for that item. The frontend did not enforce `mrn_uid` when merging results, and `mrn_or_match` used SQL `LIKE`, where `_` acts as a wildcard.
- **Fix:** An explicit MRN UID now loads coils for that UID only, with no item-wide fallback. The breakdown is also filtered client-side by `mrn_uid`, and `mrn_or_match` uses exact equality.

**Files:** `stock-adjustment/utils/minusCoilLookup.js`, `coil/models/coil.model.js`, `stock-adjustment/StockAdjustmentDrawer.js`.

### RM Store — In-process rejection via Store In; red reject badges

> Superseded by the single-row flow released on 22 Oct. Existing pairs still work.

- **Problem:** Shop-floor coils were held immediately on in-process rejection without returning through Store In, and the same coil could be rejected repeatedly.
- **Solution:** Store coils are held immediately (unchanged). Shop-floor coils go to Store In → Pending Store In and are held for the same rejection once received. A coil already on another open rejection is blocked.
- **Mechanism:** On approve, `holdCoilsForRejection` checks each coil with `isIssuedToShopFloor` (`status = out` and `out_uid`). Only those coils go into one auto Store In row (`type = return`, `stage = pending_store_in`, `remarks = AUTO_FROM_REJECTION:<ipr_uid>`). On receive, that remark links the coil to the rejection.

| Case | Result |
|------|--------|
| Generate Store Out before shop-floor coils are received | Blocked: *receive from Store In Pending first* |
| Same coil on a new rejection | Blocked: *already on in-process rejection IPR #Y* |
| Consume a coil waiting in that Store In | Blocked |
| Unapprove / delete rejection | Pending Store In cancelled; received coils remain Unassigned |

**Logs:** `auto_store_in_from_rejection`, `rejection_hold_after_store_in`, `auto_store_in_cancelled`.
**Coil table (Area):** IPR Hold → **IPR Reject**; RM Rejection → **QC Reject** (both red).

**Files:** `in-process-request/models/inProcessRequest.model.js`, `in-process-request/controllers/inProcessRequest.controller.js`, `rm-rejection/controllers/rmRejection.controller.js`, `coil/coilTableVisuals.js`.

### RM Store — Rejection Store Out: exact coil count, draft reopen, wrong coil list

- **Problem 1:** After a partial scan (e.g. 9 of 16) was saved as a draft, reopening it treated the scanned count as the rejection total. The list showed `9 / 9` and Save submitted it as complete (`scan_complete = true`). The entry moved from DRAFT to PENDING, could not be reopened as a draft, and the remaining coils were left behind. The backend did not block this because the coil-count check existed only for Job Card Store Out.
- **Problem 2:** The scan modal listed every rejected coil in the database (OUT-216 / Rejection #4 showed 23 instead of 16, including coils from rejection #3 and one coil on no rejection).
- **Fix:** The required count always comes from the rejection register. Store Out needs exactly that many coils: fewer remains a draft; more is blocked. The coil lookup now filters by the rejection link (`rm_uid`).

**Root cause of the wrong list:**
1. The modal loads coils from `/rm-rejection/get`, which needs `rm_rejection` view. Users without it got a silently caught error, which is why *Reject Reason* showed `—`.
2. The fallback called the coil helper with `{ qc_reject_uid, status: "rejected" }`.
3. `qc_reject_uid` was missing from `COIL_FILTER_KEYS`, so `sanitizeFilters` dropped it and the query became `status = 'rejected'`.
4. The required count then fell back to `fetched.length` (23).

**Required count (UI, pending list and backend):** `required = MAX(rejection.coil_count, count of coils where coil.rm_uid = qc_reject_uid)`

| Path | Change |
|------|--------|
| `frontend/.../shared/CoilScanEntryModal.js` | Draft reopen no longer seeds `coil_count` / `total_qty`; fallback lookup uses `rm_uid` |
| `frontend/.../out-entry/Page.js` | Pending **Coils** column uses `pending_coil_count ?? coil_count` |
| `backend/.../out-entry/models/outEntry.model.js` | Draft rows expose `pending_coil_count` (e.g. `9 / 16 coils`) |
| `backend/.../out-entry/controllers/outEntry.controller.js` | New `assertRejectionStoreOutComplete()` on create, update and rejection approve |

### RM Rejection — Bill list visibility by role

- **Rule:** Super admin sees all IMS `invfnote` bills (salecat 2). A normal user sees only bills matching the rejection's supplier (`acc_code`) and item (`item_code` or `item_dcode`).
- **Before:** The rule existed only in the frontend. A normal user calling `/rm-rejections/bill-helper` without filters received every bill, and the Register bill box sent no filters.
- **Now:** The backend decides by role. Super admin: filters ignored. Normal user: supplier and item are required. The frontend sends the row's supplier and item (`rejectionBillFilters(row)`).

| User | Filter sent | Result |
|------|-------------|--------|
| Super admin | (ignored) | All salecat-2 bills |
| Normal | supplier + item | Matching bills only |
| Normal | supplier or item missing | Empty list |

**Example:** Reject-4 (supplier 2124, item I-14950 / dcode 14950) has no bill because the only bill for supplier 2124 in IMS (`HPF/26-27/3183`) is for item S0013 (dcode 1530). The empty list is correct. Fix it by correcting the bill in IMS or having a super admin attach one.

**Verified (erp_db / IMS, 21 Oct):** super admin → 7 bills; normal user with no filter, supplier only, or 2124 + I-14950 → 0; normal user with 2124 + S0013 → `HPF/26-27/3183`.

**Files:** `rm-rejection/controllers/rmRejection.controller.js` (`getQcRejectionBillNumbersViews`), `lib/utils/rejectionBillOptions.js` (new `rejectionBillFilters`), `rm-rejection/Page.js`, `CompleteRejectionDrawer.js`.

No database migration.

### IMS Forwarding Note — Super admin packing FIFO start

Mirrors the RM Store Issue Request MRN FIFO start (v4.3.9), applied to packing-number order on Forwarding Note item rows.

| Topic | Summary |
|-------|---------|
| Who | `super_admin` only (`isImsSuperAdmin` and `auth.role`) |
| Default | Standard order: normal packing FIFO for everyone (unchanged) |
| Override | Super admin selects **Start at N: #packing**; box picking begins at that packing, then continues in order and wraps |
| UI | Dropdown under **Packing #** in the item breakdown table (on phones: bar above the table) |
| Persistence | Start packing is not stored; breakdown lines are saved in FIFO pick order and the start is inferred on reopen |
| Schedule hydrate fix | Stock load now passes `remaining` boxes into the FIFO calculation, so dispatch quantity and boxes populate on open instead of 0 |

| Selection | Box / dispatch FIFO |
|-----------|---------------------|

### Production — Prime Item approval, Maintain Job Card, Engineering RM wire rule

Production shortage entries are now approved per **prime item**. Approved entries feed a new **Maintain Job Card** module, where the planner selects a prime item and, for each stage of its Prime Process, one process, machine and RM; one job card is created per prime item. In Engineering, a process receives RM wire only when its Process Master **RM wire** option is ON.

| Area | Change |
|------|--------|
| Shortage → Prime Item tab | Entries grouped by prime item (from IMS item master). Select a row → Approve / Reject drawer (details, type, remark) → Save. Rejected entries can be moved back to Pending. |
| `ims_shortage` | New columns `is_approved` (NULL Pending / TRUE Approved / FALSE Rejected) and `approval_remark` |
| Shortage → Master / Item-wise | New **Weight (KG)** column = item weight × quantity, with a hover breakdown (same as IMS) |
| Maintain Job Card (new) | **Pending Shortage** (default) and **Register** tabs; row → New → stage form → job card |
| Engineering Prime / FG Process | RM Items only for processes with Process Master **RM wire** ON; otherwise empty |
| Table naming | Production tables now use the `prod_` prefix (e.g. `prod_job_card`), consistent with `ims_`, `rmstore_`, `eng_` |

#### 1. Shortage → Prime Item

**Flow:** New shortage entry (`is_approved = NULL`, Pending) → Prime Item tab shows one row per prime item → select row → Approve / Reject (type and remark both required) → Save updates all entries of that prime item → Approved / Rejected filters show them; Rejected can be moved to Pending (remark optional).

**How rows are built** (`shortage/utils/primeItemShortage.js`)

1. **Load:** `ims_shortage` rows in Production scope (not deleted, group `Production`, type `PPC` / `Additional`).
2. **Enrich:** IMS item master (cached 5 min) adds item code, description, prime item (`primitemdcode`) and item weight.
3. **Weight:** `weight_kg = item_weight × qty` (null if the item has no weight).
4. **Group:** by prime item dcode; an item without a prime item is its own prime. Each group carries `items` (qty summed per item code), `total_qty`, `total_weight_kg`, `entry_count`, `approval_remark`.
5. **List payload:** one slim row per prime item and status (`id` such as `pending-1234`), with no nested shortage lines.
6. **Expand:** `POST /production/shortage/prime-items/entries` with `{ prime_key, status? }` loads the lines for one row.
7. **RM wire (view):** `attachRmWireFromProduction` reads `rmstore_master_production.rm_items` for the prime item; the drawer shows code and description.

The prime item is not stored on the shortage row; it is read from IMS each time.

**Rules**

| Rule | Where |
|------|-------|
| Approve / Reject / Move to Pending require **Shortage → authorize** | `shortage.route.js` |
| Only rows still in the expected status are updated; an actioned row is never overwritten | `primeItem.controller.js` (`UPDATE … WHERE is_approved IS NULL`) |
| Remark required for Approve and Reject; optional for Move to Pending | Backend and drawer |
| Actor and time are recorded in the Production Activity Log, not on the shortage row | `logActivity(… appType: "production")` |

**UI (IMS style)**

- Filter strip: Status (Pending / Approved / Rejected), search, Reset / Search. Filtering runs in the browser from a single API call.
- Columns: ▸ · Prime Item · Description · Total Qty · Total Weight (KG) · Items (Qty) · Status. RM wire appears only in the Approve / Reject drawer.
- Items (Qty) shows one chip per shortage entry; hovering a chip or the weight shows item weight × quantity.
- ▸ or double-click lazy-loads entries through `/prime-items/entries`.
- Shortcuts: drawer **Esc** to close, **Ctrl+S** to submit; list **Ctrl+Alt+A** (PWA: **Ctrl+A**) to Approve; **Ctrl+C** to copy. Also Export, list / card view, 100 rows per scroll.

#### 2. Maintain Job Card

Route `/production/dashboard/job-card` · permission module `production_job_card` (view, add) · quick launch **PRJ**.

**Pending Shortage tab (default)**

- One row per prime item (approved and not-yet-approved entries merged). Rejected entries never appear; rows already on a job card are excluded.
- No expand: the payload carries `shortage_ids[]`, `items[]`, `item_codes[]`.
- Columns: Prime Item · Description · Items (Qty) · Total Qty · Total Weight (KG) · RM wire · Tooling · Status.
  - **RM wire** and **Tooling** show Yes / No / — derived from the Prime Process (any stage whose Process Master has `rm_wire` / `tooling` ON). `—` means no Prime Process is saved.
  - The same values appear under **Prime Item Details** (2-column grid) in the New / View / Edit / Approve drawer.
- Rows not yet approved are greyed out (tooltip: approve in Shortage → Prime Item first). Creation still requires every `shortage_id` to be approved.
- Filter: Approval (All / Approved / Not Approved) plus search.

**Creating a job card** (select a row → New, double-click, or **Ctrl+Alt+N**)

```
Prime Item Details (prime, qty, weight, items, RM Yes/No, Tooling Yes/No)
Process Plan · <prime item>   (per stage: Process · Machine · RM · Tooling)
Remarks
→ Save (Ctrl+S)
```

- One process per stage; single options are pre-selected, and changing the process resets machine and RM. The first process per stage (Prime Process order) is pre-selected.
- Machines: process **Multiple Job Card** ON → multi-select; OFF → single machine. The RM dropdown appears only when the process has **RM wire** ON.
- One job card per prime item: `qty` = total, `items` = `[{ itemdcode, qty }]`, `shortage_ids` = entries used. Status `Open`, approval starts Pending.
- Key = `docno` (running number). Job card number = `JC_PREFIX` + `docno` padded to `JC_PAD` digits (e.g. `JC-000001`). Prefix, padding and starting number (`JC_START`, to continue from the legacy system) are configured in `production/modules/job-card/jobCard.config.js`.
- Create body: `process_plan: [{ stage_no, process_id, machine_ids: [], rm_item_dcodes: [] }]`.
- Saved step: `{ stage_no, process_id, process_name, machines: [{ machine_id, machine_name }], rm_items: [{ rm_item_dcode, rm_item_code }] }`.
- View / Edit / Approve reuse Prime Item Details; `POST /job-card/get` adds IMS total weight, `rm` and `process_tooling` from the Prime Process.
- Register: one row per job card (Job Card No, Date, Prime Item, Items (Qty), Total Qty, Process Plan, Approval, Status) with server-side search (job card no / item / status), sort, 100 rows per scroll, Export.

**Estimated production time**

Displayed live in the New / Edit drawer and in View / Approve (`production_time` on `POST /job-card/get`). All calculation is done in the backend (`jobCardProductionTime.js`); the UI only renders the API payload (summary plus Setup / Run / Total per machine).

| Source | Fields |
|--------|--------|
| Job card | `qty` (shortage total) |
| Engineering → **approved** Prime Process Master | per machine: `setup_time`, `speed`, `duration` (seconds) |
| Drawer | `process_plan` selections |

| Step | Rule |
|------|------|
| Run | `speed > 0` → `ceil(qty / speed) × duration`; otherwise `qty × duration` |
| Machine | `setup_time + run` |
| Job | Sum of every selected machine on every stage (stages are sequential) |
| Shifts | `ceil(total_seconds / (SHIFT_HOURS × 3600))` (planning only; set `SHIFT_HOURS = 8` in that file) |

**Example (NF-1-11B6S, Nut Forging):** qty 369010, setup 2 h, speed 150, duration 1 min (60 s).

```
cycles = ceil(369010 / 150) = 2461
run    = 2461 × 60 = 147660 s  → 41 h 1 m
total  = 7200 + 147660 = 154860 s  → 43 h 1 m
shifts (this stage) = ceil(154860 / 28800) = 6 @ 8 h
```

Adding further stages (e.g. Tapping) gives 106 h 32 m, or 14 shifts, for the full job.

An incomplete plan returns `valid: false` with `plan_error` (e.g. missing machine); Save is blocked and the estimate is hidden until valid.

| Call | When |
|------|------|
| `POST /production/job-card/estimate-production` | While editing: `{ item_dcode, qty, process_plan[] }` |
| `calcJobCardProductionTime` | On get / create, using the saved plan and approved prime stages |

Frontend: `job-card/jobCardProductionEstimate.js` (hook and Est. Production Time section; no client-side math).

**Backend validations** (`jobCard.controller.js`)

| Check | Error |
|-------|-------|
| Every shortage id exists and is in Production scope | `Shortage entry not found` |
| Every entry is prime-approved (`is_approved = TRUE`) | `Not approved: … Approve them in Production → Shortage → Prime Item first.` |
| Entry is not already on a job card (checked after a row lock, safe under parallel clicks) | `Already used in a job card` |
| A Prime Process is saved for the prime item | `No prime process saved…` |
| Each stage: process belongs to the stage, machine and RM belong to the process | `Stage N: select a process / machine / RM.` |

#### 3. Engineering — RM wire rule

| Process Master → RM wire | Prime / FG Process form → RM Items |
|---|---|
| ON | RM wire from Item RM Master (as before) |
| OFF | Empty; RM removed on save |

- The process dropdown (`/engineering/process-master/helper`) now returns `rm_wire`.
- On save (`savePrime`, `saveFg`), RM is removed from processes with RM wire OFF (`validateStages` in `itemProcess.model.js`).
- On read (`loadStages`), the current `rm_wire` is attached to every saved process, so existing forms follow today's Process Master setting. Old JSON with RM on an OFF process is cleaned on the next save.

#### 4. Prime / FG process — own table (Engineering only)

A single table, `eng_item_process`, where each row is one process plan. It has no link to `rmstore_master_production`, whose RM is only read as the form's default.

| Column | Meaning |
|--------|---------|
| `id` | Plan id |
| `type` | 1 = prime, 2 = fg |
| `item_dcode` | Item of this plan (prime item for type 1, FG item for type 2) |
| `process` | JSON, same shape for both types (key order preserved) |
| `is_approved` | `true` / `false` / NULL (pending); new saves start pending |
| `approved_by`, `approved_at` | Set on approve; cleared when the plan is edited |

There is no id link between rows; an FG finds its prime through the item. Example: HN006 is a prime item and HN006, HN006TW and HN006Y are built on it → one prime row (type 1, HN006) plus three finish rows (type 2). The prime of a finish item is the IMS `primitemdcode` of that item (live, not stored).

```json
{ "type": "prime",
  "stages": [ { "stage": 1, "processes": [ { "process": 1, "machines": [1, 2], "rm": [1451] } ] } ] }

{ "type": "fg",
  "stages": [ { "stage": 1, "processes": [ { "process": 12, "machines": [20], "rm": [] } ] } ] }
```

The JSON stores ids only; names come live from Process / Machine Master and RM codes from IMS. There is one active row per (`type`, `item_dcode`). **Saving an FG is refused if its prime has no plan.**

| Action | Behavior |
|--------|----------|
| Save prime | PRIME items only (IMS `primitemdcode` = itself); inserts or updates its row, and every FG on it sees the change |
| Save FG | Saves the FG item's own row against its prime item's prime |
| Approve / reject plan | Sets `is_approved`, `approved_by`, `approved_at`; editing a plan resets it to pending. Job card and estimated time use **approved prime only** (`findPrimeIdsByItems`, default `approvedOnly: true`). UI: Approve drawer on the Prime / FG Process Master list. API: `POST …/prime-item-master/approve`, `POST …/finish-process-master/approve` with `{ id, approved }` |
| Delete prime | Blocked (409) while any finish row's item has this prime item in IMS |
| Delete FG | Removes that row only |
| RM per process | RM wire ON → pre-selected from the prime item's Item RM (production) in DB order (serial = priority); config `prime_item_rm_wire_selectable = true` lets the user change it. RM wire OFF → no RM |

**API** (`/engineering/prime-item-master/*`, `/engineering/finish-process-master/*`): `list`, `get { id | item_dcode }`, `create` / `update { item_dcode, process: { stages } }`, `delete { id }`.
**Row shape:** `{ id, type, item_dcode, item_code, item_desc, prime_item_code (live from IMS), rm_items, process, prime_process, fg_process, audit }`.

| Item | File |
|------|------|
| Table | `backend/.../engineering/lib/config/tables/item-process/item_process.table.js` |
| Save / delete / read | `backend/.../engineering/modules/item-process/models/itemProcess.model.js` |
| API | `backend/.../engineering/modules/item-process/controllers/itemProcess.controller.js` |
| Job card | `jobCard.model.js` — `loadPrimeProcesses` (unchanged) |

**Adding a field to the JSON** (e.g. `cycle_time`): add one line each in `toLine` (save) and `fromLine` (read) in `itemProcess.model.js`, then add the input in `ProcessStagesBlock.js`. No database change is needed, and older rows without the field keep working. To remove a field, delete those lines.

**Process flags** (`rm_wire`, `tooling`, `prime`, `fg`, …) are defined in one place (`PROCESS_FLAGS` in `processMaster.model.js`). They are not stored in the JSON and are always read from Process Master. `rm_wire` OFF means the process has no RM. The Prime form lists only processes with `prime` ON; the Finish form lists only processes with `fg` ON.
