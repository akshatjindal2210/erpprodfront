## v5.1.0 — Inventory Audit unified (IMS + RM Store)

### 16 Oct 2026

RM Store **Inventory Audit** and IMS **Audit** used the same workflow (assign locations → freeze expected → scan → compare → score → optional adjustment) but **duplicate PostgreSQL tables** (`rmstore_audit_master` / `rmstore_audit_locations` vs `ims_audit_master` / `ims_audit_locations`). RM had **no production audit data**, so we merged onto the IMS tables and kept RM/IMS apps separate only by **`app_type`** and coil vs box snapshot logic.

### Why

| Before | After |
|--------|--------|
| Two table pairs, two DDL paths, ~duplicate list SQL | One pair: `ims_audit_master`, `ims_audit_locations` |
| Risk of divergent bugs (copy-paste models) | Shared list query; per-app models for coil/box only |
| RM locations already on `ims_location_master` | Audits also on shared IMS-named tables with `app_type = 'rmstore'` |

IMS existing audits stay valid: new column **`app_type`** defaults to **`ims`**; list/get/create/update/delete for each app filter by `app_type`.

### Behaviour (unchanged for users)

| App | Permission | Stock unit | API |
|-----|------------|------------|-----|
| IMS | `audit` | Box UID in JSON | `/api/audit/…` |
| RM Store | `rm_inventory_audit` | Coil UID in same JSON columns | `/api/rmstore/inventory-audit/…` |

- DB columns remain **`expected_boxes`** / **`scanned_boxes`** (RM stores **coil-shaped** JSON inside them).
- RM API/list still exposes **`expected_coils`** / **`scanned_coils`** via SQL aliases (UI unchanged).
- Coil stock / MRN / adjustment still use **`rmstore_coil_table`** — not merged with `ims_box_table`.

### Score (unchanged formula)

Per location, after expected vs scanned UID compare:

`score% = round( max(0, matched − extra) / expected × 100 , 2 )` where `matched = expected − |missing|`.

Saved to `ims_audit_locations.score_pct` when a location closes. Logic in each app’s `audit.model.js` (`computeLocationScorePct`).

### DB / boot

| Item | Detail |
|------|--------|
| **`ims_audit_master.app_type`** | `'ims'` \| `'rmstore'` — patched on IMS audit DDL |
| **Legacy drop** | `backend/src/config/db/legacyTableDrops.js` → `runLegacyTableDrops()` from `initDB()` after app table init; drops `rmstore_audit_locations` then `rmstore_audit_master` (`IF EXISTS`, every boot) |
| **Registry** | `rmstore_audit_*` removed from `dbTables.js`; `moduleTableMap`: `rm_inventory_audit` → `ims_audit_master` |
| **RM DDL folder** | Removed `rmstore/lib/config/tables/audit/` — no RM-specific audit CREATE |

No RM data migration. Run backend once so `app_type` column exists on existing DBs.

| RM start snapshot SQL error `column m.mrn_uid does not exist` | MRN join: `rmstore_mrn.uid = coil.mrn_uid` (not `m.mrn_uid`) |

## v5.1.0 — Production Prime Item approval · Maintain Job Card · Engineering RM wire rule

### 15 Oct 2026

Production shortage entries are now approved per **prime item**. Approved entries feed a new **Maintain Job Card** module: the planner picks a prime item and, for each stage of its Prime Process, one process, a machine and RM. A job card is created for each item. In Engineering, a process now gets RM wire only when its Process Master **RM wire** option is ON.

| Area | Change |
|------|--------|
| **Shortage → Prime Item tab** | Entries grouped by prime item (from IMS item master). Select a row → **Approve / Reject** button → drawer: details, Type (Approve / Reject), remark → **Save**. **Move to Pending** for rejected entries |
| **`ims_shortage`** | 2 new columns: `is_approved` (NULL Pending / TRUE Approved / FALSE Rejected) and `approval_remark` |
| **Shortage → Master / Item-wise** | New **Weight (KG)** column = item weight × qty; hover shows the calculation (same as IMS) |
| **Maintain Job Card** (new module) | **Pending Shortage** (default) + **Register** tabs. Row → **New** → stage form → job card |
| **Engineering Prime / FG Process** | RM Items only for processes whose Process Master **RM wire** is ON (cell empty otherwise) |
| **Table names** | Production prefix is now `prod_` (`prod_job_card`), like `ims_`, `rmstore_`, `eng_` |

## 1. Shortage → Prime Item

### Flow

```
New shortage entry → is_approved = NULL (Pending)
  → Prime Item tab: one row per prime item (all its entries inside)
  → select row → "Approve / Reject" → drawer: pick Type + remark (both required) → Save → all entries of that prime item updated
  → Approved / Rejected filter shows them; Rejected → Move to Pending (remark optional)
```

### How rows are built (`backend/.../shortage/utils/primeItemShortage.js`)

1. **Load** — `ims_shortage` rows of the Production scope: not deleted, group `Production`, type `PPC` / `Additional`.
2. **Enrich** — IMS item master (cached 5 min) adds item code / description / **prime item** (`primitemdcode`) / item weight.
3. **Weight** — `weight_kg = item_weight × qty` (null when the item master has no weight).
4. **Group** — key = prime item dcode; an item without a prime item is its own prime item. Each group has `items` (qty summed per item code), `total_qty`, `total_weight_kg`, `entry_count`, `approval_remark`.
5. **List payload** — slim row per prime **and status** (`id` = `pending-1234`, …). No nested shortage lines in the list response.
6. **Expand** — `POST /production/shortage/prime-items/entries` with `{ prime_key, status? }` loads shortage lines for one row only.
7. **RM wire (view)** — `attachRmWireFromProduction`: RM Store **Production master** (`rmstore_master_production.rm_items`) for the prime item → drawer shows code + description (not Process Master).

Prime item is **not stored** on the shortage row — it is read from IMS each time.

### Rules

| Rule | Where |
|------|-------|
| Approve / Reject / Move to Pending need **Shortage → authorize** permission | `shortage.route.js` |
| Only rows still in the expected status are updated (an already actioned row is never overwritten) | `primeItem.controller.js` — `UPDATE … WHERE is_approved IS NULL` |
| Remark required for Approve and Reject, optional for Move to Pending | backend + drawer |
| Who / when → **Production Activity Log** (not stored on the shortage row) | `logActivity(… appType: "production")` |

### UI (IMS style)

- Filter strip: **Status** (Pending / Approved / Rejected) + search + Reset / Search. Filter runs in the browser — **one API call** loads all statuses.
- Columns: ▸ · Prime Item · Description · Total Qty · Total Weight (KG) · Items (Qty) · Status (no RM column in table; RM wire only in approve/reject drawer).
- Items (Qty) = **one chip per shortage entry** (same item codes can appear more than once).
- ▸ / double-click → lazy-load entries via `/prime-items/entries`. Hover a chip / weight → item weight × qty.
- Drawer: **Esc** close, **Ctrl+S** submit. List: **Ctrl+Alt+A** (PWA **Ctrl+A**) → Approve. **Ctrl+C** copy, **Export**, list / card view, 100 rows per scroll.

## 2. Maintain Job Card

Route `/production/dashboard/job-card` · permission module **`production_job_card`** (view, add) · quick launch **PRJ**.

### Pending Shortage tab (default)

- **One row per prime item** (approved + not-yet-approved entries merged for that prime). Rejected entries never appear. Rows already on a job card are excluded.
- **No expand** — list payload has `shortage_ids[]`, `items[]`, `item_codes[]` (no nested `children`).
- Columns: **Prime Item · Description · Items (Qty) · Total Qty · Total Weight (KG) · RM wire · Tooling · Status** (no Approval Remark column).
  - **RM wire** / **Tooling** = **Yes / No / —** from **Prime Process** (any stage whose Process Master has `rm_wire` / `tooling` ON). `—` = no Prime Process saved.
  - Same Yes/No in **New / View / Edit / Approve** drawer → **Prime Item Details** (2-column grid).
- Not-approved rows are grey (tooltip: approve in Shortage → Prime Item first). Create still requires every `shortage_id` to be approved.
- Filter: **Approval** (All / Approved / Not Approved) + search.

### New job card (select row → **New**, double-click, or **Ctrl+Alt+N**)

```
Prime Item Details (2 cols: prime, qty, weight, items, RM Yes/No, Tooling Yes/No)
Process Plan · <prime item>  (stage table: Process · Machine · RM · Tooling per stage)
Remarks
→ Save (Ctrl+S)
```

- One process per stage. Single options are pre-selected. Changing the process resets machine and RM.
- **One job card per prime item** — `qty` = total, `items` = item-wise qty (`[{ itemdcode, qty }]`), `shortage_ids` = entries used. Status `Open`, starts Pending.
- Key = `docno` (running number). Job card no = `JC_PREFIX` + `docno` padded to `JC_PAD` digits (`JC-000001`).
  Change prefix / digits / first number (`JC_START`, to continue after the old system) in `backend/.../production/modules/job-card/jobCard.config.js`.
- Register = one row per job card (Job Card No, Date, Prime Item, Items (Qty), Total Qty, Process Plan, Approval, Status).
- **View / Edit / Approve** — same **Prime Item Details** block; `POST /job-card/get` adds IMS **total weight**, `rm`, `process_tooling` from prime process.
- New / Edit drawer — per stage: **first process** pre-selected (prime process order, change from dropdown, one per stage).
  Machines: process **Multiple Job Card** ON → multi-select, OFF → one machine. RM dropdown only when process **RM wire** ON.
  Create body: `process_plan: [{ stage_no, process_id, machine_ids: [], rm_item_dcodes: [] }]`.
  Saved step = `{ stage_no, process_id, process_name, machines: [{ machine_id, machine_name }], rm_items: [{ rm_item_dcode, rm_item_code }] }`.

### Backend checks (`jobCard.controller.js`)

| Check | Error |
|-------|-------|
| Every shortage id exists and is Production scope | `Shortage entry not found` |
| Every entry is prime-approved (`is_approved = TRUE`) | `Not approved: … Approve them in Production → Shortage → Prime Item first.` |
| Entry not already in a job card (checked after a row lock → safe for parallel clicks) | `Already used in a job card` |
| Prime Process saved for the prime item | `No prime process saved…` |
| Each stage: process from that stage, machine from that process, RM from that process | `Stage N: select a process / machine / RM.` |

### Register tab

Job card list — server search (job card no / item / status), sort, 100 rows per scroll, Export.

## 4. Prime / FG process — own table (Engineering only)

One table, `eng_item_process` — one row = one process plan. **No link to `rmstore_master_production`** (nothing stored there; its RM is only read as the form's default RM).

| Column | Meaning |
|--------|---------|
| `id` | plan id |
| `type` | 1 prime · 2 fg |
| `item_dcode` | the item of this plan — prime item (type 1) or FG item (type 2) |
| `process` | JSON, **same shape for both types** (keys keep their order) |

No id link between rows — an FG finds its prime by item. Example: HN006 is the prime item; HN006, HN006TW, HN006Y are built on it →
1 prime row (type 1, HN006) + 3 finish rows (type 2, HN006 / HN006TW / HN006Y). The prime of a finish item = IMS `primitemdcode` of that item (live, not stored).

```json
{ "type": "prime",
  "stages": [ { "stage": 1, "processes": [ { "process": 1, "machines": [1, 2], "rm": [1451] } ] } ] }

{ "type": "fg",
  "stages": [ { "stage": 1, "processes": [ { "process": 12, "machines": [20], "rm": [] } ] } ] }
```

Ids only — names live from Process / Machine Master, RM codes from IMS. Put a prime and its FG side by side and `type` tells which is which.
One active row per (`type`, `item_dcode`). Prime item of an FG = IMS `primitemdcode` (else itself). **No prime → FG save is refused.**

| Action | What happens |
|--------|--------------|
| Save prime | PRIME items only (IMS primitemdcode = itself); insert or update its row — every FG on it sees the change |
| Save FG | the FG item's own row, on its prime item's prime |
| Delete prime | blocked (409) while any finish row's item has this prime item in IMS |
| Delete FG | that row only |
| RM per process | RM wire ON → pre-selected with the prime item's Item RM (production) RM, in its DB order (serial = priority); app config `prime_item_rm_wire_selectable` = true lets the user change it. RM wire OFF → no RM |

API (`/engineering/prime-item-master/*`, `/engineering/finish-process-master/*`): `list`, `get { id | item_dcode }`, `create` / `update { item_dcode, process: { stages } }`, `delete { id }`.
Row: `{ id, type, item_dcode, item_code, item_desc, prime_item_code (live from IMS), rm_items, process, prime_process, fg_process, audit }`.

| Step | File |
|------|------|
| Table | `backend/.../engineering/lib/config/tables/item-process/item_process.table.js` |
| Save / delete / read | `backend/.../engineering/modules/item-process/models/itemProcess.model.js` |
| API | `backend/.../engineering/modules/item-process/controllers/itemProcess.controller.js` |
| Job card | `jobCard.model.js` — `loadPrimeProcesses` (unchanged) |
| UI list | `frontend/.../engineering/modules/process-mapping/ItemProcessPage.js` (Prime + FG pages) |
| Old data | `backend/src/migrations/v5.1.0/processJsonToTables.js` (old Item RM JSON) → `processSelfContained.js` (FG item_dcode from finish_id, `stages` → `process`, earlier JSON `"finish"` → `"fg"` + `item_dcode` / `prime_item_dcode` removed, then drops `stages`, `prime_id` and `rmstore_master_production.prime_id / finish_id`) |

**New field in the JSON** (e.g. `cycle_time`)
1. In `itemProcess.model.js` add one line in `toLine` (save) and one line in `fromLine` (read).
2. Add its input in the form (`ProcessStagesBlock.js`).

That's all. No DB change. Old rows without the field still work.
To remove a field, delete those lines.

**Process flags** (`rm_wire`, `tooling`, `prime`, `fg`, …)
- The list is in one place: `PROCESS_FLAGS` in `processMaster.model.js`.
- They are not saved in the JSON. They are always read from Process Master — ON there = `true`, OFF there = `false`.
- `rm_wire` OFF → that process has no RM.
- Prime form takes only processes with `prime` ON. Finish form takes only processes with `fg` ON.
