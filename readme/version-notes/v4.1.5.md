## B. ERP Stock Report — fast DB query

|           |                                      |
|-----------|--------------------------------------|
| **UI**    | IMS → ERP Stock Report               |
| **API**   | `POST /api/erp-stock-report/list` (same body / response) |
| **DB**    | New **index only** — no table/column change |
| **Dates** | **11 Sep 2026**                      |
| **Version note** | Builds on [v4.1.4](./v4.1.4.md) row identity (packing + date + job + item) |

## Problem

The report became slow. `sqlDailyprodLateralForBox` ran on every **in-hand box** (`doc_no::text` OR integer) — thousands of correlated lookups. JS also received **one row per box**; ERP attach scanned the full merged list.

## What changed (same totals, faster path)

Row identity **unchanged** (v4.1.4):

```
packing_number + doc_dt + job_card_no + item_dcode
```

Customer still display-only (comma-joined). Stock **not** split by customer.

### 1. SQL — set-based, then aggregate

`ERP_STOCK_DB_SQL` in `erpStockComparisonList.js`:

1. **`in_hand`** — in-hand boxes + SA join (qty > 0)
2. **`pack_keys` / `best_dp`** — dailyprod **once per packing** (numeric → `doc_no` PK; non-numeric → text). **No per-box LATERAL**
3. **`GROUP BY`** packing + item + date + job — `SUM(qty)`, `STRING_AGG` customers

Plain `LEFT JOIN ims_dailyprod ON packing = doc_no` still **must not** be used (one packing can match extra dailyprod rows and double `SUM(qty)`).

### 2. JS merge

- SQL already grouped — `mergeDbAndErpRows()` safety-net + ERP attach
- ERP attach: `packing::item` map (no full-table scan per ERP line)
- Concurrent loads share one in-flight build (`reportGen` so a later Refresh does not overwrite with stale cache)

### 3. Index

```sql
CREATE INDEX IF NOT EXISTS idx_box_in_hand_stock
  ON ims_box_table (packing_number)
  WHERE is_deleted = false
    AND out_uid IS NULL
    AND (sa_entry_type IS DISTINCT FROM 'stock_out')
    AND COALESCE(qty, 0) > 0
```

## What did NOT change

| Area | Status |
|------|--------|
| API contract / FE table / filters / export | Same |
| ERP FG fetch (`erpfg`) | Same (still cached) |
| Item master + ledger name resolve | Same |
| Inventory report / box list / FN | Untouched (`sqlDailyprodLateralForBox` still used there) |
| v4.1.4 one-row-per-key rule | Same |

## Small edge (rare)

SA box has **item but empty date/job** — dailyprod could sometimes fill these before; it no longer does (stock qty unchanged).

## Proper flow

1. Open **New QC Hold**.
2. Select one action from first step: `On Hold`, `On Submit`, or `Revert`.
3. If `On Hold` is selected, choose scan type: `Full Hold` or `Partial Hold`.
4. If `On Submit` is selected, choose submit type: `Partial Submit` or `Full Submit`.
5. Titles and subtitles are explicit at each step, so the active flow is always clear.

## Hold input flow

1. Full Hold input accepts either **Packing Number** or **Job Card**.
2. Backend resolution order:
   - first tries input as packing
   - if not found, tries Job Card in `ims_dailyprod`
   - if still not found, falls back to Job Card in `ims_stock_adjustment`
3. Matching packings are expanded and all valid in-hand sellable boxes are loaded.

## Submit and approval flow

1. Partial submit (non-final) is applied directly and reduces hold balance immediately.
2. Final closing partial submit goes to approval queue.
3. Full submit goes through approval flow.
4. One-time approval behavior is preserved (already-approved submission cannot be re-approved without a new business action).

## Transaction and audit flow

1. Transaction labels are clearer:
   - `Partial submitted`
   - `Partial submitted - awaiting approval` (final partial)
   - `Partial approved`
2. Non-final partial no longer shows an extra `APPROVE` transaction row.
3. `updated_by` / `updated_at` are now written only on real edit/update, not on submit/approve/print.
4. Deleted QC Hold entries are hidden from transaction logs by default (`SHOW_DELETED_HOLD_LOGS = false`).

## H. Schedule Item Wise — Dispatch % column

| | |
|--|--|
| **UI** | Schedule Planning → **Schedule Item Wise** (column after **Dispatch Qty**) |
| **API / DB** | No change — UI only; uses existing row fields |
| **Dates** | **12 Sep 2026** |

## What

Shows how much of the scheduled quantity has already been dispatched, as a percentage.

## Logic

```
Schedule Qty  = row.schedule_qty  (fallback: row.totalqty)
Dispatch Qty  = row.dispatch_qty  (sum from forwarding notes — already on list rows)

Dispatch %    = round( Dispatch Qty ÷ Schedule Qty × 100 )

If Schedule Qty = 0  →  Dispatch % = 0%
If Dispatch Qty = 0  →  Dispatch % = 0%
```

**Note:** `Balance Qty = Schedule Qty − Dispatch Qty` (backend already enriches this).  
**Dispatch %** is display-only — no new API or DB field.

## Examples

| Schedule Qty | Dispatch Qty | Balance Qty | Calculation | Dispatch % |
|-------------:|-------------:|------------:|-------------|----------:|
| 200,000 | 0 | 200,000 | 0 ÷ 200,000 × 100 | **0%** |
| 75,000 | 47,500 | 27,500 | 47,500 ÷ 75,000 × 100 = 63.33… → round | **63%** |
| 6,000 | 6,000 | 0 | 6,000 ÷ 6,000 × 100 | **100%** |
| 75,000 | 75,000 | 0 | fully dispatched | **100%** |

**Step-by-step (e.g. Sch No 25638):**

1. Schedule Qty = **75,000**
2. Dispatch Qty = **47,500** (from forwarding notes)
3. `47,500 / 75,000 = 0.6333…`
4. `0.6333 × 100 = 63.33`
5. `Math.round(63.33)` → displays **63%** in the column

## Implementation — column

Frontend only — calculated from existing list fields (`dispatch_qty`, `schedule_qty` / `totalqty`):

| File | Change |
|------|--------|
| `frontend/.../schedulePlanningColumns.js` | **Dispatch %** column · `scheduleDispatchPct()` · `attachScheduleDispatchFields()` |

```js
export function scheduleDispatchPct(row) {
  const sch = Number(row?.schedule_qty ?? row?.totalqty ?? row?.total_qty ?? 0);
  return sch > 0 ? Math.round(Number(row?.dispatch_qty ?? 0) / sch * 100) : 0;
}
// display + copy/export: `${scheduleDispatchPct(row)}%`
```

Search/sort run in the browser on loaded rows — **no new API**.

## I. Forwarding Note — approval + over-dispatch %

| | |
|--|--|
| **UI** | IMS → Forwarding Note (New / Edit / Approve modal + list) |
| **API** | `POST /forwarding-notes/create` · `POST /forwarding-notes/update` (same routes) |
| **DB** | No schema change — uses existing `approved_*`, `created_*`, `updated_*` on master |
| **Config** | `forwarding_shortage_qty_percentage` (App Configuration) |
| **Dates** | **12 Sep 2026** |

## Why

1. **Approval** — Forwarding Note needed the same create / update / approve timestamp rules as Location Master and Packing Standard.
2. **Over-dispatch %** — When `forwarding_shortage_qty_percentage > 0`, the cap was `balance + %` only. That blocked valid **standard FIFO qty** (full-box pick) when it was higher than the tolerance cap (e.g. balance 490 + 10% = 539, but one full box = 3,000).
3. **False validation** — Approve-only and blur on Dispatch Qty could write `updated_by/at` or show “Cannot exceed maximum allowed quantity” even when the user did not change anything.

## 1. Approval workflow (aligned with Location Master)

Uses shared `approval.js` helpers — same rules as section **C**.

| Action | Timestamps |
|--------|------------|
| Create pending | `created_by/at` only |
| Create + approve | `created` + `approved` (`approved_at = created_at`) |
| Approve only (no edit) | `approved_by/at` only — **not** `updated_*` |
| Edit | `updated_by/at` |
| Edit + approve | `updated` + `approved` |
| Edit approved record | Status → **Pending** on normal Save |
| Re-approve without edit | **Blocked** (409 + Approve button disabled) |

**Backend fixes**

- Removed model auto-set `updated_at` on every master update (was forcing false “Updated” on approve-only).
- Update uses `applyApprovalUpdateFields` + normalized field compare; approve-only sends changed header fields only.
- Approve-only path: `items: []` → re-validates saved lines, does **not** replace boxes in DB.

**Frontend**

- Approve button disabled when row is already approved.
- Approve mode sends `items: []` when boxes were not edited (FIFO-safe).
- **Save & Approve** on Edit when user has `authorize` permission (same as Location Master).
- Per-button loading spinner (Save / Keep Pending / Approve / Save & Approve).

## 2. Over-dispatch tolerance % (`forwarding_shortage_qty_percentage`)

| Config | Behaviour |
|--------|-----------|
| **`0` / unset** | Unchanged — FIFO targets balance; full-box overshoot allowed (e.g. balance 10,000 → std 1,210). No max-allowed toast. Backend skips schedule max check. |
| **`> 0`** | Hidden cap = `balance + floor(balance × pct / 100)`. **Allowed max = max(tolerance cap, standard FIFO qty at balance, current Std QTY).** User cannot exceed that max. |

**Examples (`pct = 10`)**

| Balance | Tolerance cap | Standard (boxes) | Allowed |
|--------:|--------------:|-----------------:|--------:|
| 10,000 | 11,000 | 1,210 | **11,000** |
| 490 | 539 | 3,000 | **3,000** |

**Why not `min(FG, tolerance)` for typed target?**  
Schedule rows store **balance** as the dispatch target; **Std QTY** from full boxes can differ. Validation compares against the schedule max above, not FG alone — fixes false “Cannot exceed maximum allowed quantity” on blur.

**FIFO unchanged** — same `calculateFifoBoxes`, box order, +/- stepper, exclusive pool, save/reserve logic.

## Approval / activation workflow

| Action | Timestamps |
|--------|------------|
| Create inactive | `created_by/at` only |
| Create + activate | `created` + `activated` (`approved_at = created_at`) |
| Activate only (no edit) | `activated_by/at` only — **not** `updated_*` |
| Edit inactive audit | `updated_by/at` (business change only) |
| Edit + Save & Activate | `updated` + `activated` |
| Already active → activate again | **Blocked** (409 + button disabled) |
| Active audit → edit | **Blocked** (delete & recreate — unchanged business rule) |

**Backend**

- Removed unconditional `updated_at` on every update.
- Uses `applyApprovalUpdateFields` with field-level change detection (dates, remarks, assignments).
- Create + activate: insert first, then approve with `approvalTimestamp = created_at`.
- Activate-only body: `{ approved: true }` only.

**Frontend**

- **Activate** toolbar button (Master tab) + **Ctrl+A** hotkey.
- Edit: **Save & Activate** + **Update**; create: optional Active toggle + **Save**.
- Approve drawer: **Keep Inactive** + **Activate**; form read-only in activate mode.
- Per-button loading (`activeSubmit`); **Ctrl+S** → Update/Save only.
- List columns: Updated By/At, Activated By/At.

| | |

## What changed

### 1. Master tab

- Opens **by default**; **Reset** returns to Master-wise.
- **Types / Total Shortage / Balance** = sum of **Authorized (approved)** entries only — pending rows excluded.
- **No Status filter** on Master (Type + Report only).
- Totals from **backend SQL** (`GROUP BY` item + month + `SUM(qty)`), not frontend math.
- **Pack / Balance** unchanged — pack from monthly packing usage; balance = approved total − pack.
- **Item code click** → Item-wise tab, same item + month, Status **Authorized** (drill-down).

### 2. Item-wise tab

- Default Status = **Pending** (was effectively all / inconsistent before).
- Status filter: **All / Authorized / Pending** (Item-wise only).
- Switch to Item-wise tab → Status resets to **Pending**.

### 3. Group (`grpname`) on form

- After **Item** select → **Group** dropdown (default from item master; user can change).
- Same on **Add / Edit / Approve**; sub-user limited edit = group read-only.
- Saved `grpname` on row wins over IMS lookup on list (fixes wrong group after save).
- Legacy blank rows: see section **E** (backfill).

### 4. FY / date / list load

- **Default report** = full selected **Financial Year** (not current month only).
- Custom month filter no longer breaks when view-days clamp mid-month.
- Helpers: `resolveShortageListDateRange`, `clampMonthFieldRange`, `fullRangeInIndianFy`.

### 5. Quick search

- **All Status** on Item-wise: `useDeferredValue` — typing stays fast; filter runs in background.
