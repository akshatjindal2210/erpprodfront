## v3.4.38 — IMS Box: dispatched SA-add box shown as in-store (13C)

Stock-adjustment **add** boxes that later go out via **Out Entry** could still show **location 13C** in the box list and Box Finder, while a sibling box from the **same** dispatch correctly showed **DISPATCH**.

|           |                                                                 |
|-----------|-----------------------------------------------------------------|
| **UI**    | IMS → Boxes list · Box Finder                                   |
| **API**   | Box list `stock_zone` · inventory SQL (in-hand / outward / SA minus) |
| **DB**    | No schema change — `ims_box_table.sa_id` + `out_uid` + `sa_entry_type` |
| **Scope** | IMS Boxes classification                                        |
| **Dates** | **2 Sep 2026**                                                  |

Release: [v3.4.38.md](./v3.4.38.md)

## Issue

Two boxes of the same item left on the **same** out entry (`OUT-366`, 08 Jul 2026, Rajkumar, 28 boxes). Journey on **both** is `OUT — DISPATCHED`. UI treated them differently.

| Box sticker | `sa_id` | `out_uid` | List / Finder (before) |
|-------------|---------|-----------|-------------------------|
| `26_20669_SA366_1_1` | **366** | **366** | Location **13C**, Finder “Box is here” |
| `26_4890_SA367_1_1` | 367 | 366 | Blue **DISPATCH** badge, Finder “Dispatched” |

`26_20669_SA366_1_1` was **not** in rack 13C (already out). The row stayed white / 13C because classification never reached `dispatched`.

### Why (root cause)

Boxes created by stock-adjustment **add** keep `sa_id` from that add (`SA366` in the sticker). Later dispatch sets `out_uid` to the out-entry id and **does not** clear `sa_id`.

Old rule:

```
out_uid === sa_id  →  treat as stock-adjustment minus (removed), not dispatch
```

That marker is valid for real **minus** (`sa_entry_type = stock_out`, `out_uid` copied from `sa_id`).

Here the numbers **collided by chance**:

- Box `SA366` was created by stock adjustment **366** (`sa_entry_type = stock_in`)
- Same box was dispatched on out entry **366**
- `366 === 366` → false **minus**
- Box `SA367` had `sa_id` 367 ≠ `out_uid` 366 → correctly **dispatch**

`location_id` stays on the row after dispatch (by design). Finder only hides store place when zone is `dispatched`. Misclassified box still loaded rack **13C**.

```
  Box list / Finder
        │
        ▼
  isBoxStockAdjustmentOut?
        │
        ├─ sa_entry_type = stock_out          → minus (correct)
        ├─ out_uid empty                      → not minus
        └─ out_uid === sa_id                  → minus  ← BUG when stock_in + colliding ids
                │
                ▼
  isBoxOutwardDispatch = false
  isBoxInHand = false (out_uid set)
        │
        ▼
  stock_zone = removed / other
  Location cell = leftover 13C (plain text)
  Finder = “Box is here”
```

---

## Solution

If the box is a stock-adjustment **add** (`sa_entry_type = stock_in`), a later `out_uid` is **dispatch**, even when `out_uid === sa_id`.

```
  isBoxStockAdjustmentOut
        │
        ├─ sa_entry_type = stock_out   → minus
        ├─ sa_entry_type = stock_in    → NOT minus (dispatch if out_uid set)
        ├─ out_uid empty               → not minus
        └─ out_uid === sa_id           → legacy minus only when NOT stock_in
```

Frontend zone no longer trusts API `stock_zone` first (old payload could still say `removed`). Live checks run first: QC hold → outward dispatch → in hand → then API zone.

After the fix, `26_20669_SA366_1_1` matches `26_4890_SA367_1_1`: **DISPATCH** badge, Finder “Dispatched”, store location hidden.

No data migration. Existing rows are correct; only classification was wrong.
