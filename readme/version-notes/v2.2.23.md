### IMS — Loose sticker misclassified as Open/Full box (Forwarding Note + Out Entry)

**Problem:**
- A loose sticker (TYPE LOOSE, e.g. packing `#37363`, 206 PCS) appeared under **OPEN BOXES** in the Forwarding Note breakdown instead of **LOOSE BOXES**.
- Out Entry scan failed with: `Limit reached for packing #37363: only 0 standard boxes required` — the FN required **1 loose / 0 standard**, but the scan counted the box as standard.

**Cause:**
- When only one loose sticker exists and its qty equals the packing standard (206 = 206), the old logic treated it as full/open using qty comparison only.
- Startup `backfillBoxIsLooseFromPackingMode` could set `is_loose = false` when qty matched the inferred standard.
- The Sticker screen uses `full_boxes_count` + box UID index for LOOSE; Forwarding Note and Out Entry used raw `ims_box_table.is_loose` + qty rule only.

**Fix:**
- Added `isLooseStickerIndex()` — when `ims_dailyprod.full_boxes_count` is set (including `0`), box UID index greater than full count → loose. Skipped when snapshot is `null` (legacy packings unchanged).
- Added `isForwardingLooseBox()` — priority: `is_loose` flag → sticker index → qty vs `qty_per_box`.
- API payloads now pass `qty_per_box`, `full_boxes_count`, `loose_box_qty` from dailyprod on available boxes, box lookup, and Out Entry FUID details.
- Backfill only upgrades `is_loose` to `true`; never downgrades `true` → `false`.
- FIFO, reserve, full-box selection, save validation, and advisory lock — unchanged.

**Reflects:**
- Forwarding Note → item breakdown: loose stock under **LOOSE BOXES**
- Forwarding Note → save: correct `loose_box` / `box` in `ims_forwarding_note_item_wise`
- Out Entry → packing area: **Loose 1** instead of **Full 1**
- Out Entry → scan: **LOOSE BOXES 1/1**; scan accepted
- Out Entry → approve: standard vs loose fulfillment match

### Dashboard Builder — Published container grey box stretch / overlap

**Problem:**
- In the builder, widgets inside a container looked correct, but after **publish** the grey container box was taller than its content (empty grey space above/below).
- Nested widgets sometimes overlapped or were clipped — saved nested `h` was bloated and the publish view stretched the full grid cell with `h-full`.

**Cause:**
- On publish, the container wrapper used `h-full` + `flex-1`, so the grey shell filled the grid cell beyond its content.
- Saved nested layout `h` could be much larger than the actual widget (e.g. 6 rows for a small KPI).
- Main grid container row height was not recalculated on publish — old saved `h` was kept.

**Fix:**
- `containerCellHeightClass()` returns `h-auto` for containers (other widgets stay `h-full`).
- `WidgetRenderer` — publish/read-only container shell uses `h-auto overflow-visible` instead of stretch `flex-1`.
- `resolvePublishedDesktopLayout()` recalculates container `h` via `containerAutoGridHeight()` on publish load.
- `compactLiveLayoutForDisplay()` auto-grows container rows and repacks vertically on live view.
- CSS rules for `.container-widget-cell > div.h-auto` in builder and live view grids.
- `ContainerNestedGrid` read-only mode renders saved x/y/w/h via CSS grid (builder parity).

**Reflects:**
- Home / IMS / Task published dashboard — grey container fits widgets tightly
- Dashboard Builder live preview — container height matches nested content
- KPI / table / graph inside containers — less overlap and clipping
- Re-publish recommended if old saved layout still has bloated `h`
