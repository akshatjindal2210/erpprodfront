## Part A — Dashboard user filter & Quick Access (26 Aug 2026)

### Problem (before)

| Issue               | Detail                                                                                        |
|---------------------|-----------------------------------------------------------------------------------------------|
| Super Admin only    | **ALL USERS** dropdown on live dashboards was effectively limited to Super Admin              |
| Admin / EA blocked  | Admin and Executive Assistant could see dashboards but could not filter org-wide user data    |
| No manager scope    | Users with **Manager** designation had no team-level filter — only self data                  |
| Client-only rules   | Filter visibility was mostly frontend; spoofing another user’s ID was possible                |
| Quick Access gaps   | Home portal hid Quick Access; app shortcuts were not consistently permission-filtered         |

### Solution (after)

```
                    getDashboardUserFilterScope()
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
      "all"              "department"            "self"
  SA / Admin / EA      Manager designation    Everyone else
  org-wide list        dept users only        no user dropdown
        │                     │                     │
        └──────── resolveWidgetFiltersForUser() ────┘
                    (backend enforces scope)
```

| Role / designation | User dropdown | Widget data scope |
|--------------------|---------------|-------------------|
| **Super Admin** | All Users (org) | Any selected user or all |
| **Admin** | All Users (org) | Same — server validated |
| **Executive Assistant** | All Users (org) | Same — server validated |
| **Manager** (designation on `user`) | All Team (dept) | SQL restricted to department members |
| **Other users** | Hidden | Always own data only |

**Quick Access:** Shown on Home, IMS, RM Store, and Task shells. Links are filtered by module permission and app access. Help stays on the far right; date/user/refresh filters sit to its left on dashboard pages.

### Why these changes

- Operations leads (Admin, EA) need the same dashboard drill-down Super Admin already had.
- Managers need department team views without seeing the full organisation.
- Backend enforcement prevents tampering with `df_uid` / `df_user` query params.
- Quick Access on Home improves navigation for plant users who land on the portal first.

## Part B — CL Task Master Edit: multi Person(s) (26 Aug 2026)

### Problem (before)

| Issue | Detail |
|-------|--------|
| Edit locked to one person | On **Edit**, Assign step **Person(s)** was forced to **single-select** via `lockToPerson` |
| Add/Clone inconsistency | Add and Clone already allowed **multiple persons**; Edit did not |
| UX confusion | Users could create multi-assignee masters but could not add/remove persons when editing |

### Solution (after)

- Removed `lockToPerson` single-select lock on Edit.
- **Add, Clone, and Edit** all use `SearchableSelect` with `isMulti` + `compactMulti` for **Person(s)** when Assign by = **Person**.
- **Assign by** toggle (Department/Designation vs Person) remains available on Edit, same as Add/Clone.
- Backend already accepted `assignee_person_ids` on update — no API change required.

### Why this change

- Master task definitions should be editable without recreating from scratch when assignees change.
- Edit behaviour now matches create/clone, reducing training burden and support tickets.

### Files — CL Task Edit

| File | What changed | Why |
|------|--------------|-----|
| `frontend/src/apps/task/modules/cl-task/shared/ClAssigneeSection.js` | Removed Edit single-person lock; Person(s) always multi-select; Assign by toggle always enabled | Core fix — Edit = Add/Clone for assignees |
| `frontend/src/apps/task/modules/cl-task/admin/ClTaskModal.js` | Wizard passes `isEdit` / `isClone`; save payload includes `assigned_user_ids` / `assignee_person_ids` | Same modal for all modes; backend-compatible payload |

**Not changed:** CL Task **submission** edit (`updateClTaskSubmission`) — completed-instance rules, verifier permissions, and Super Admin completed edit remain as before.

## Part C — Normal Task: Rating & Super Admin (27 Aug 2026)

### Problem (before)

| Issue | Detail |
|-------|--------|
| No performance score | Assigners had no structured way to rate completed assigned work |
| Super Admin gaps | Super Admin could not reliably edit/delete/complete **any** task; list was participant-scoped |
| Completed = inconsistent | Detail page showed read-only for completed tasks, but list/hotkeys could still open Edit |
| Chat label | Completion chat used `[Final Approval]` instead of `[Completed]` |
| No rating in reports | Exports and tables had no rating column |

### Solution (after)

#### 1. Rating column & Final Approve flow

```
Assigned task completion:
  … → creator_pending → Assigner (or Super Admin) Final Approve
                              │
                              ├─ Rating 1–10 required (assigned tasks only)
                              ├─ Saved to task_tasks.rating
                              └─ Chat: [Completed] Rating: X/10 — remark
```

| Rule | Applies to |
|------|------------|
| Rating **required** on Final Approve | `task_type = assigned` |
| Rating **not used** | Self tasks, recurring templates, CL tasks |
| DB constraint | `rating IS NULL OR (rating BETWEEN 1 AND 10)` |
| Super Admin rating change | Via **Edit modal** only (single Save with other fields) |

#### 2. Super Admin / Admin full manage access (normal tasks)

| Action | Super Admin | Admin |
|--------|-------------|-------|
| View any task (list + detail) | Yes | Yes (list scope + manage) |
| Edit / delete any task (incl. completed) | Yes | Yes |
| Forward, L1 approve/reject, Final Approve | Yes | As participant / staff rules |
| **Force / Admin Complete** | **Yes — only Super Admin** | No |
| Change rating after complete (Edit modal) | Yes | Yes |
| Chat on completed tasks | Yes | Yes |

#### 3. Everyone else — owner rules (pehle jaisa)

- **Edit / Delete:** Self task → **creator**; Assigned task → **assigned_by** only.
- **Completed tasks:** Owners keep edit/delete (not blocked solely for completed status).
- **Rating:** Required on Final Approve for assigned tasks; after complete, only SA/Admin change via Edit.
- **List Actions:** Do **not** gate on portal `can_edit` / `can_delete` for module `"tasks"` (that module is not in portal permissions — it always returned false and hid Edit/Delete).

### Why these changes

- Business asked for a simple 1–10 score when closing **assigned** work, separate from CL verification scoring.
- Super Admin / Admin need override power for support; force-complete stays Super Admin–only.
- Server-side + shared `taskManageAccess` keep list/detail/card consistent.

## Part D — Task list Actions Edit/Delete fix (27 Aug 2026)

### Problem (before)

| Issue | Detail |
|-------|--------|
| Actions missing Edit/Delete | List showed only View / Activity / Clone even for **Assigned By = me** |
| Root cause | UI checked `useCanAccess("tasks", "edit"|"delete")` but **`"tasks"` is not a portal module** → always denied for non–super_admin |
| Assign Task still visible | Plain buttons (not ActionButton) so add worked while edit icons stayed hidden |

### Solution (after)

```
showEdit / showDelete =
  super_admin | admin     → always
  other roles             → isOwner (self = created_by, assigned = assigned_by)
```

Matches backend `canManageTask`. No change to assign / complete / approve flows.

## Part E — CL Task Report: no-verify score, date window, today column (27 Aug 2026)

### 1. No-verify completed tasks → full score

| Case | Done? | Score |
|------|-------|-------|
| Verify on + rating 1–10 | Yes | `(rating ÷ 10) × 100%` |
| **Verify off** (or scoring off) + **completed** | Yes | **10/10 = 100%** (was wrongly 0%) |
| Awaiting verification / pending / missed | No | 0% |

**Why:** Tasks without a verifier still count as work done; they must contribute to Score %, not sit as Done with 0%.

### 2. Default date range (controllable)

| | Pehle | Ab |
|--|-------|-----|
| From | Today − 2 | Today − **7** |
| To | Today + 7 | Today + **2** |

Change both places together:

| Constant | File |
|----------|------|
| `REPORT_DEFAULT_DAYS_BACK` / `FORWARD` | `backend/.../reports/reportDateRange.config.js` |
| Same names | `frontend/.../lib/services/reportApi.js` |

Set `DAYS_BACK` to `10` (or any N) when a longer past window is needed.

### 3. Today column UI

- Soft emerald highlight + **bold** weekday/date text.
- Single control object: `TODAY_COLUMN` in `ReportBookingCalendar.js` (header/body/section bg + text classes).

### Files — CL Report

| File | What changed | Why |
|------|--------------|-----|
| `backend/.../reports/controllers/reportPanel.controller.js` | `effectiveScore` / `fillEffectiveScore` → 10 when no-verify completed; default range from config | Score + BE default dates |
| `backend/.../reports/reportDateRange.config.js` | `REPORT_DEFAULT_DAYS_BACK` / `FORWARD` | One-knob BE defaults |
| `backend/.../reports/helpers/reportScore.helper.js` | `REPORT_SCORE_FORMULAS.no_verify` text | Score Formula panel |

## Known limitations (by design)

| Item | Note |
|------|------|
| Super Admin **force-complete** | May complete without rating; rating can be added later in Edit |
| Rating clear to NULL | Not exposed in UI; only change between 1–10 |
| Portal module `"tasks"` | Still not registered — manage UI uses ownership/staff, not `can_edit` |
| FE/BE date defaults | Must keep `REPORT_DEFAULT_DAYS_*` in sync in two files |
| Pre-existing | Activity log / chat GET endpoints lack strict task-level access checks (unchanged) |
