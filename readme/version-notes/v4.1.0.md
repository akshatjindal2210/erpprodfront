### 1. HRMS — new app

New **HRMS** app added to ERP for attendance from Hikvision device punches + daily summary.

| Module | Purpose |
|--------|---------|
| Attendance Log | Raw device / manual punch rows |
| Daily Attendance | One row per employee + date (first / last punch) |

**Tables:**
- `hrms_attendance_log` — punch log
- `hrms_attendance` — daily aggregate (`UNIQUE (employee_code, attendance_date)`)

**Ingest:**
- Device webhook → parse AccessControllerEvent → insert log
- Manual mark (In / Out) from portal
- After each valid punch → upsert daily attendance

**Key mapping:**
- Device `dateTime` → `event_timestamp`
- Daily `attendance_date` / check-in / check-out from that timestamp (IST `Asia/Kolkata`)
- Failed events (e.g. Human Detection Failed) stay in log only — not counted as daily present

**UI:**
- Attendance Log columns align with DB fields
- Date & Time shown in one column

**Files (backend):**  
`attendanceEvents.js`, `attendanceDaily.js`, `attendanceLog.controller.js`, `attendance.controller.js`, `attendance_log.table.js`, `attendance.table.js`, portal modules / `dbTables.js`

**Files (frontend):**  
`attendanceLogColumns.js`, Attendance Log / Attendance pages, HRMS nav / routes / services

### 2. IMS Audit — Random location assign

**Problem:** Assigning many locations per user by hand is slow.

**Solution (optional; manual select unchanged):**
1. Select users in assignment rows
2. Enter **count / user** (e.g. 10)
3. Click **Random** (with Shuffle icon)

**Logic:**
- Shuffle all approved locations each click (not always same rack/side)
- Each user gets `count` **unique** locations (no overlap)
- Save / validate / backend payload unchanged

**Files:** `AuditModal.js`

### 3. IMS Audit — Expected boxes freeze on Start (not Create)

**Problem:** Expected boxes were snapshotted when the audit was **created**. If audit runs days later, store in/out changes stock — scan expected becomes wrong.

**Solution:**
| When | Expected boxes |
|------|----------------|
| Audit create / new location row | Empty (`[]`) — no snapshot |
| User **starts** their assigned location | Live in-hand boxes frozen |
| After first box scan | Snapshot stays locked |
| Reassign (new active row) | Starts empty → new user start freezes again |

**API:** `POST /audit/start-location`  
Called when assignee opens Start for their location.

**Safety:**
- Closed location → no re-freeze
- Location already has scans → keep existing expected
- First box submit also calls ensure (backup if Start was skipped)

**Files:**  
`audit.model.js` (`ensureExpectedBoxesAtScanStart`, create/reassign insert), `audit.controller.js`, `audit.routes.js`, `Page.js` (`openAuditExecution`), endpoints / `audit.js` service

### 4. IMS QC Hold Material — Activity History

Operators can open a **History** drawer on a QC hold and see create / submit / approve (and related) events as a readable timeline. Logging and history fetch are scoped to QC Hold only — the shared IMS / RM / Task **Activity Logs** APIs and pages are unchanged.

#### 4.1 History drawer (frontend)

- Opens from the QC Hold list via **History**
- Shows events newest-first (timeline with action badges)
- Summary and extra fields use a normal key–value layout (not raw JSON dumps)
- Empty noise is hidden: `0`, `[]`, `{}`, blank values
- Nested data (e.g. boxes, submissions) is shown as lists / small cards
- Legacy rows that only stored `hold_data: {...}` offer **Show details** using the current hold’s `hold_data` (best-effort for old rows)

**Files:**  
`QcHoldActivityDrawer.js`, `Page.js` (qc-hold-material), `qcHoldMaterial.js` service, `endpoints.js`

#### 4.2 Dedicated activity API (backend) — POST only

Shared `GET /api/core/activity-logs` stays as-is so existing Activity Log pages are not affected.

```http
POST /api/qc-hold-material/activity-log
Content-Type: application/json

{ "hold_id": 21, "limit": 200 }
```

- Permission: `qc_hold_material` → `view`
- Returns all users’ events for that hold
- Validates hold exists before returning logs

**Files:**  
`qcHoldMaterial.controller.js` (`getQcHoldActivityLog`), `qcHoldMaterial.routes.js`

#### 4.3 Richer activity payloads on write

Create / submit / approve / update logs pass a compact `hold_data` snapshot into activity details. QC Hold builders store clear `info` / `more` fields and nested `hold_data` where useful. Object summaries can expand one nesting level instead of only `{...}`.

**Files:**  
`qcHoldMaterial.controller.js`, `activityLogPayload.js`

#### 4.4 What did not change

| Area | Status |
|------|--------|
| Shared Activity Logs (IMS / RM / Task) | Unchanged — still `GET /api/core/activity-logs` |
| `activityLogService.getLogs` | Unchanged — still GET + query string |
| QC Hold create / submit / approve business rules | Unchanged (logging / history UI only) |
