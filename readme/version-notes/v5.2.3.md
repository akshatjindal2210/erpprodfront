# Release Notes — v5.2.3 (29 Oct 2026)

Module notification templates: template cloning, condition value suggestions, and UI integration in Training and Settings.

See also: [v5.2.0](./v5.2.0.md) (conditions UI), [module-notifications.md](../module-flow/admin-console/module-notifications.md).

---

## Overview

| Feature | Description |
|---------|-------------|
| **Clone** | Duplicate a template with name suffix ` (Copy)`, new id and timestamps. |
| **Conditions** | Optional `{ field, operator, value }` rules with AND/OR logic; empty list means always send. |
| **Field values** | API-backed value suggestions for conditions; users may still enter custom values. |

**Permissions:** Clone requires template **add**; field-values requires **view** (permission module: `training_videos`).

---

## Clone template

**UI**

- Training & SOPs → notification template list: Copy icon per row (add permission, not view-only).
- Settings → Notifications → Templates: Copy in the Actions column.

**API**

```http
POST /api/core/notification-templates/clone
{ "id": <templateId> }
```

Copies module, content, audience, triggers, conditions, and channel settings. Rejects duplicate names within the same module.

**Key files:** `notificationTemplate.controller.js` (`cloneNotificationTemplate`), `notificationTemplate.routes.js`, `notificationTemplateService.js`, `endpoints.js`, `NotifyTemplateListModal.js`, `ModuleTemplatesTab.js`, `training/Page.js`.

## Conditions

**Form** (`NotificationTemplateModal.js`): Field (module column hints + free text), operator, value, AND/OR logic, add/remove rows.

**Persistence:** Existing create/update endpoints; `conditions` and `condition_logic` stored as JSONB.

**Runtime:** `notificationConditions.js` evaluates against record variables in `moduleNotify.service.js` at dispatch time (no change to delivery channels in this release).

## Field values API

```http
POST /api/core/notification-templates/field-values
{ "module_id": <number>, "field": "<column>" }
→ { "success": true, "data": ["...", "..."] }
```

**Security:** Field names must match `[a-z_][a-z0-9_]*` and exist on the module primary table (or approved virtual fields: `department`, `designation`, `department_id`). Table/column identifiers are never interpolated from unvalidated input.

**Suggested values:** `SELECT DISTINCT column::text` from the module primary table (max 100), whitelisted column names only. Virtual condition fields `department`, `designation`, and `department_id` use DISTINCT on the corresponding master tables.

Values appear in the dropdown only after at least one row stores that value in the column (e.g. `failed` is not listed until a `failed` row exists). Users can enter any value manually (`SearchableSelect` + `allowFreeText`). Changing the field clears the value.

**Key files:** `moduleRecordFieldsFromDb.js` (`distinctValuesForModuleField`), `notificationTemplate.controller.js` (`getNotificationFieldValues`), `notificationTemplate.routes.js`, `notificationTemplateService.js`, `NotificationTemplateModal.js` (`ConditionValueSelect`).

## Out of scope

- No new npm dependencies.
- No config table, CHECK constraints, or hardcoded per-column value maps for field-values.
- Field-values queries only the module primary table (plus virtual master fields); no ad-hoc SQL from client input.
