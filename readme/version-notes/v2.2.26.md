### Forwarding Note — Direct create via special permission

**Problem:**
- After v2.2.25, Master **New** was schedule-only for everyone.
- Some users still need to create a Forwarding Note **without** a schedule (blank add modal), while most users must stay on the schedule path.

**Cause:**
- Module View / Add / Edit alone could not separate “schedule create” from “direct create”.
- There was no IMS special permission for direct Forwarding Note create (unlike Inventory Out / Inventory Approve).

**Fix:**
- New IMS special permission: **Direct Forwarding Note** (`special_permissions.ims.direct_forwarding_note`).
- **Same New button** on both tabs (shown when module **Add** is allowed):
  - **Today's Dispatch Plan** → always schedule-based create (`schno`).
  - **Forwarding Note** (master) → blank add modal **only** if Direct Forwarding Note is granted; otherwise toast: use Today's Dispatch Plan.
- Backend: create without `schno` requires the special permission (403 if missing). Schedule-based create (`schno` present) needs only module Add.
- Super Admin keeps direct create (same pattern as other IMS special permissions).
- No DB migration — uses existing `special_permissions` JSONB.

**Flow:**
1. User with Forwarding Note **Add** → Today's Dispatch Plan → select schedule row → **New** → FN from schedule
2. Same user **without** special permission → Forwarding Note tab → **New** → toast (use schedule tab)
3. User with **Add** + **Direct Forwarding Note** → Forwarding Note tab → **New** → blank add modal (no schedule)
4. Admin: Identity → Users → Edit → IMS Special Permissions → tick **Direct Forwarding Note** → save → user refresh / re-login

**Reflects:**
- Admin → Edit User → IMS Special Permissions → **Direct Forwarding Note** checkbox
- Forwarding Note → both tabs keep one **New** button; behaviour depends on tab + special permission
- API rejects direct create without permission

**Files:**
- `backend/src/apps/ims/utils/imsSpecialPermissions.js` — `hasDirectForwardingNotePermission`
- `backend/src/apps/ims/controllers/forwardingNote.controller.js` — create without `schno` gated

- `frontend/src/features/apps/ims/utils/imsSpecialPermissions.js` — `canCreateDirectForwardingNote`
- `frontend/src/features/apps/ims/components/forwarding-note/ForwardingPage.js` — Master New / direct vs schedule toast
- `frontend/src/features/admin/identity/users/UserModal.js` — Direct Forwarding Note checkbox

### Forwarding Note — Direct create: Boxes + grows with FIFO

**Problem:**
- On **direct** Forwarding Note (no schedule), after typing Dispatch Qty (e.g. 2000 → 1 box), the Boxes **+** button stayed disabled even when FG stock and more boxes were available (e.g. `1 / 22`).
- Users expected free-form behaviour: **+** should add more FIFO boxes and raise Dispatch Qty up to available stock.

**Cause:**
- Boxes **+** max was tied to the current typed Dispatch Qty / FIFO target, so the stepper froze at the boxes already selected for that qty.
- Schedule balance cap (`source_dispatch_qty`) was not separated from direct / no-schedule rows.

**Fix:**
- **Schedule** rows (`source_dispatch_qty` > 0): Boxes **+** still stops at balance qty (unchanged).
- **Direct** / no schedule: Boxes **+** allows all available boxes in FIFO order; each **+** updates Dispatch Qty / Std Qty from the selected prefix.
- Dispatch Qty typing still caps at FG stock when there is no balance; schedule typing still caps at balance.

**Flow:**
1. Direct FN → pick item → type Dispatch Qty (or start from 0)
2. Boxes **+** / **−** adjust FIFO selection; Dispatch Qty follows selected box total
3. Schedule FN → **+** still limited by remaining balance

**Reflects:**
- Forwarding Note modal → Boxes stepper on direct create
- Schedule path balance gate unchanged

**Files:**
- `frontend/src/features/apps/ims/components/forwarding-note/ForwardingModal.js` — `maxFifoBoxesForItem` / Boxes +/- for direct vs schedule

### Inventory Report — Location Details box count + hover list

**Problem:**
- **Location Details** showed only location labels (e.g. rack/shelf).
- Users could not see how many boxes sit under that packing row, or which `box_no_uid` values they are, without opening another screen.

**Cause:**
- Report SQL returned location aggregate only; it did not expose box count / box list for Total Stock zones.
- Location cell rendered plain text with no tooltip.

**Fix:**
- Additive SQL fields (stock qty / zone logic unchanged):
  - `stock_box_count` — box count for **Total Stock** zones only (**In Store + Packing Area**)
  - `stock_box_nos` — `box_no_uid` list for those same boxes
- **QC hold** boxes are **not** in the count/list (same rule as Total Stock — QC stays in **QC Hold Area** column only).
- Location Details cell shows: `R1A, R2B (3)` — locations + count in brackets.
- Hover on the cell → comma-separated box list (`box_no_uid`).

**Flow:**
1. Open Inventory Report
2. **Location Details** → location text + `(n)` box count
3. Hover count/cell → which boxes (`box_no_uid`) make up that count

**Reflects:**
- Inventory Report → Location Details column: count beside location; hover for box list
- Count aligned with Total Stock (excludes QC hold)

**Files:**
- `backend/src/apps/ims/utils/inventory-report/inventoryReportSql.js` — `stock_box_count`, `stock_box_nos` (STOCK_BOX = in store + packing)

- `frontend/src/features/apps/ims/components/inventory-report/Page.js` — Location cell render: `(count)` + hover tooltip

### Forwarding Note — Schedule vs direct paths kept separate

**Problem:**
- Edit / Approve always opened the customer **schedule** item catalog, even for **direct** notes (no schedule).
- Direct notes could pick up schedule lines, get `schno` stamped incorrectly, and lose free in-hand item add.
- On edit of a schedule note, **Balance** often showed **0** because the current note’s dispatched qty was counted against itself.

**Cause:**
- `customerSchedulePicker` was forced on for every edit/approve.
- Dispatch balance map did not exclude the note being edited (`exclude_fuid`).

**Fix:**
- Schedule catalog only when:
  - Add from **Today’s Dispatch Plan** (blank New or row prefill), or
  - Edit / Approve of a note that already has `schno` on header or items (`loadedAsScheduleNote`).
- Direct Master New / direct edit uses **in-hand** available items only; never stamps schedule `schno` onto empty-schno rows.
- `loadScheduleDispatchQtyMap({ excludeFuid })` + modal `exclude_fuid` so edit balance includes qty already on this note.
- Customer-month schedule picker hides lines with remaining balance **0** (and excludes Complete / Reject).
- FG **0** lines may still show (distinct style) but cannot be added; Bal **0** cannot be added.
- Unused `DispatchSchedulePickModal.js` removed (catalog lives in the FN modal).

**Flow:**
1. Super Admin / Direct FN permission → Forwarding Master → **New** → pick in-hand items → save (no schno)
2. Today’s Dispatch Plan → **New** → customer schedule catalog → Sch + Bal → save (item-wise schno)
3. Edit schedule FN → items stay selected; Balance reflects remaining including this note
4. Edit direct FN → in-hand catalog; no schedule injection

**Reflects:**
- Forwarding Note modal → Search Item options differ by schedule vs direct
- Edit Balance badge / schedule hint for schedule-linked notes
- API create still gates direct (no schno) via special permission / super admin

**Files:**
- `backend/src/apps/ims/utils/schedule-planning/schedulePlanDb.js` — `excludeFuid` on dispatch qty map
- `backend/src/apps/ims/utils/schedule-planning/schedulePlanService.js` — customer-month schedules + Bal > 0 filter
- `backend/src/apps/ims/routes/schedulePlanning.route.js` — customer-month schedules (view)

- `frontend/src/features/apps/ims/components/forwarding-note/ForwardingModal.js` — `scheduleCatalogActive` / `loadedAsScheduleNote` / Bal enrich / FG·Bal guards
- `frontend/src/features/apps/ims/components/forwarding-note/ForwardingPage.js` — `customerSchedulePicker` rules
- `frontend/src/features/apps/ims/services/schedulePlanning.js` — customer-month schedules client
- Removed: `DispatchSchedulePickModal.js`

### Forwarding Note — Today’s Dispatch Plan status filters

**Problem:**
- Status filter **All** mixed open and finished work and was easy to misread.
- Users needed clear **Pending**, **Hold**, **Complete**, and a true **All**, with default **Pending + Hold**.

**Cause:**
- Default was `all` but backend treated `all` as Plan + Hold only (no Complete status rows).
- **Complete** meant balance 0 among Plan/Hold only; marked Complete (`is_planned = 3`) never appeared under All.

**Fix:**
| Filter | Result |
|--------|--------|
| **Pending + Hold** (default) | Planned + Hold, remaining balance > 0 |
| **Pending** | Planned only, balance > 0 |
| **Hold** | Hold only, balance > 0 |
| **Complete** | Status Complete **or** remaining balance = 0 |
| **All** | Planned + Hold + Complete (any balance) |

**Flow:**
1. Open Forwarding Note → Today’s Dispatch Plan
2. Default list = open Pending + Hold
3. Switch **Complete** / **All** to review finished or full set

**Reflects:**
- Today’s Dispatch Plan → Status quick filter
- Row legend: Zero balance / Complete styling

**Files:**
- `backend/src/apps/ims/utils/schedule-planning/schedulePlanService.js` — `parseDispatchStatusFilter` / balance modes
- `backend/src/apps/ims/utils/schedule-planning/schedulePlanDb.js` — Complete allowed in dispatch status set

- `frontend/src/features/apps/ims/components/forwarding-note/ForwardingPage.js` — filter options + default `active`
- `frontend/src/features/apps/ims/components/forwarding-note/TodayDispatchPlanTab.js` — default + Complete row style
