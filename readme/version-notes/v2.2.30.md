## v2.2.30 — Forwarding Note: one item once per note *(18 Jul 2026)*

---

### Forwarding Note — Unique item (same item not twice on one FN)

**Problem:**  
Today’s Dispatch Plan → **New** (no row) → customer → item dropdown mein agar **do schedules same item** (e.g. SCH 25241 + SCH 25253, dono HN005) hon, to dono rows ek hi FN par add ho sakte the. Usse same item ke liye do FIFO picks ho sakte the (overlapping boxes / confusing qty). Qty freeze se stock side manage hota hai, lekin UI confusing thi.

**Simple rule (fix):**  
**Ek Forwarding Note mein ek `item_dcode` sirf ek baar** — dusre Sch No se bhi same item add nahi hoga.

**Frontend:**
1. Item dropdown: jo item already kisi row par hai, uska koi bhi schedule line list se hide.
2. Dobara select try → toast: *This item is already on this note…*
3. Row select → **New** (prefill): same customer ki lines, **per item pehli line** (selected row prefer).
4. Dusre schedule ka balance → **alag Forwarding Note**.

**Backend (secure):**  
Create / update item save pe payload validate:
- Same `item_dcode` do baar → **400** (API bypass block)
- Same `box_no_uid` do item rows pe → **400** (FIFO overlap block)  
Note: save ke baad DB mein same item ke **alag packing** rows normal hain — uniqueness sirf modal/payload lines par.

**FIFO:**  
Break nahi. Ek item = ek row = ek FIFO pick. Double-claim risk hat gaya.

**Process note (bug nahi):**  
Same item ke do open schedules → do FNs. Ek note par merge supported nahi.

**Test:**
1. UI: New (no row) → HN005 SCH A add → SCH B / HN005 hide; toast on force.
2. API: create/update with two items same `item_dcode` → 400.
3. API: two items sharing same `box_no_uid` → 400.
4. Normal multi-item FN (different items) + multi-packing same item after save → OK.
