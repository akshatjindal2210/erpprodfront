## Schedule Planning — version notes *(17 Jul 2026)*

---

### Status model — Ready vs Plan vs Hold

**Problem:**
- One “planned” flag mixed authorize and dispatch-date planning.
- Hold / Ready / Plan / Reject / Complete needed clear codes and transitions.

**Cause:**
- Older `is_planned` meanings overlapped; no dedicated Hold; Plan was not a separate stage after Ready.

**Fix:**
- Canonical `is_planned` codes (shared FE + BE):
  - `0` Pending · `1` Ready to Dispatch · `2` Plan · `3` Complete · `4` Reject · `5` Delete · `6` Hold
- Every change writes `ims_schedule_plan_transaction` (`plan` | `ready` | `hold` | `reject` | `complete`).
- Deprecated aliases (`PLANNED` / `RUNNING` / `SCHEDULE`) not used.

**Flow:**
1. IMS line → Pending  
2. Authorize → Ready or Hold  
3. Add → Plan (date) / Reject / Complete  
4. Plan with due date → Today’s Dispatch Plan  

**Reflects:**
- Schedule Planning status badges + filters
- Dispatch helper only uses Plan (and Complete tab rules)

**Files:**
- `backend/src/apps/ims/utils/schedule-planning/schedulePlanStatus.js`
- `frontend/src/features/apps/ims/components/schedule-planning/schedulePlanStatus.js`
- `backend/src/apps/ims/config/tables/schedule_plan.table.js`

### Permissions — Add vs Authorize (+ Super Admin)

**Problem:**
- Same users could not be split: who authorizes vs who plans dates.
- Super Admin hit the same transition walls as normal users.

**Cause:**
- Routes and UI did not consistently map actions to `add` vs `authorize`.
- No super-admin bypass on status gates.

**Fix:**
- Module `schedule_planning`:
  - **Authorize** → Hold, Ready to Dispatch, Shortage  
  - **Add** → Plan, Reject, Complete  
  - **Delete** → remove plan data  
  - **View** → list / history / action-dates  
- Super Admin: `canTransitionAsSuperAdmin` bypasses status gates (still needs route permission unless both flags are granted).
- Add + Authorize users open the full Plan modal (not authorize-only).

**Flow:**
1. Sales / approver → Authorize → Ready or Hold  
2. Planner (Add) → Plan / Reject / Complete on Ready (also from Hold)  
3. Super Admin → any non-delete transition without “from current status” dead-ends  

**Reflects:**
- Schedule Planning toolbar Plan / Authorize button label by permission
- API 403 vs 400 “Cannot … from current status”

**Files:**
- `backend/src/apps/ims/routes/schedulePlanning.route.js`
- `backend/src/apps/ims/controllers/schedulePlanning.controller.js` — `scheduleActionOpts`

- `frontend/src/features/apps/ims/components/schedule-planning/Page.js`

### Transitions — who may move where

**Problem:**
- Plan → Ready failed for Add+Authorize users (“Cannot mark Ready to Dispatch from current status”).
- Hold blocked Add (Plan / Reject / Complete) even when product needed Hold → Plan.
- Approvers needed Hold after Plan / Reject, and Reject → Hold.

**Cause:**
- `canReadyFrom` omitted Plan; `canPlanFrom` / `canRejectFrom` / `canCompleteFrom` omitted Hold; FE hid Hold rows from Add-only modal.

**Fix:**
- **Ready from:** Pending, Ready, Hold, Reject, **Plan**  
- **Hold from:** Pending, Ready, Plan, Reject  
- **Plan / Reject / Complete from:** Ready, Plan, **Hold**  
- Add-only modal includes Hold rows so Hold → Plan is usable  

**Flow:**
1. Plan item → Ready (re-authorize) works for Authorize users  
2. Hold item → Plan / Reject / Complete works for Add users  
3. Reject / Plan → Hold works for Authorize users  

**Reflects:**
- Authorize / Plan modal action dropdown + submit APIs

**Files:**
- `backend/.../schedulePlanStatus.js` — `canReadyFrom` / `canHoldFrom` / `canPlanFrom` / …
- `frontend/.../schedulePlanStatus.js` — `canReadyFromStatus` / `isAddWorkableStatus` / `filterScheduleItemsForPermission`
- `frontend/.../SchedulePlanModal.js` — submit guards aligned with BE

### List filters + role defaults

**Problem:**
- Sales approvers needed Pending plus holds that are due; non-sales approvers should stay on plain Pending.
- Add users still need Ready-first default.

**Cause:**
- Single Pending filter; no Pending + Hold; defaults not role/dept-aware.

**Fix:**
- New filter **Pending + Hold** = Pending IMS lines + Hold where hold `action_date` ≤ today (future holds stay under **Hold** only).
- Defaults (`getDefaultScheduleStatusFilter`):
  - Super Admin → Pending + Ready  
  - **Authorize + Sales dept** → Pending + Hold  
  - **Authorize, not Sales** → Pending  
  - **Add** → Ready to Dispatch (unchanged)  
- List still loads `status: all` from API; FE chips filter client-side (`matchesFrontendStatusFilter`).

**Flow:**
1. Sales + Authorize login → opens Pending + Hold (due holds visible with Pending)  
2. Non-sales Authorize → Pending only  
3. Add user → Ready to Dispatch  
4. Manual chip switch still available for all filters  

**Reflects:**
- Schedule Planning status quick filter strip

**Files:**
- `frontend/.../schedulePlanStatus.js` — `PENDING_HOLD`, `isHoldDueOrPast`, defaults
- `frontend/.../Page.js` — filter match + empty states
- `backend/.../schedulePlanStatus.js` — `PENDING_HOLD` + `isHoldDueOrPast`
- `backend/.../schedulePlanService.js` — `buildFilteredList` case `pending_hold`

### Authorize / Plan modal UX

**Problem:**
- Apply-to-all Ready on mixed statuses failed or felt unsafe; new authorize forms offered “No change”.
- Holding one of many items re-saved everything; previous hold/plan date was prefilled as value.
- Header Plan / Reject / Complete looked disabled for Super Admin / Add+Approve (false pending).

**Cause:**
- Bulk header passed `rowStatus=null` → treated as Pending → disabled Add actions.
- Authorize defaulted all rows to Ready/Hold; dates copied from last action into the input value.

**Fix:**
- **New Pending authorize:** no “No change”; default **Ready to Dispatch**; Ready or Hold required; Hold date mandatory.
- **Existing rows:** “No change” allowed so one item can Hold/Ready without touching others.
- Previous date = **placeholder only** (not value).
- Bulk “Apply to all” uses `forBulkApply` (options not falsely disabled).
- Clearer toast when Hold date missing.

**Flow:**
1. Open Authorize on Pending schedule → all lines Ready by default  
2. Change only needed lines to Hold + pick date → Authorize  
3. Re-open later → No change on untouched lines; selective Hold still works  

**Reflects:**
- Schedule Plan / Authorize drawer (header + per-row Action / date)

**Files:**
- `frontend/.../SchedulePlanModal.js`

### Today’s Dispatch Plan (Forwarding Note)

**Problem:**
- Dispatch list needed only dated Plan work for the current month through today; Hold must not appear.
- Complete vs open Plan needed balance-aware tabs.

**Cause:**
- Older helpers mixed statuses; Hold could leak into dispatch helpers.

**Fix:**
- `POST /dispatch-helper`: same month; last plan/complete txn `action_date` from month-start → today.
- **Plan** tab: status Plan + `balance_qty` > 0; sort balance high → low.  
- **Complete** tab: Complete, or Plan with balance ≤ 0.  
- **No Hold** on Today’s Dispatch Plan.  
- FG stock + FN dispatch balance enrichment unchanged in spirit.

**Flow:**
1. Add saves Plan + `action_date`  
2. Forwarding Note → Today’s Dispatch Plan → row appears (if date ≤ today, same month, balance > 0)  
3. FN qty raises dispatch → balance drops → Complete tab / Complete status  

**Reflects:**
- Forwarding Note → Today’s Dispatch Plan tab
- Customer-month schedule picker excludes Hold / Complete / Reject

**Files:**
- `backend/.../schedulePlanDb.js` — `loadDispatchPlanItems`
- `backend/.../schedulePlanService.js` — `listScheduleDispatchPlan`, `listCustomerMonthSchedules`
- `frontend/.../forwarding-note/TodayDispatchPlanTab.js`
- `backend/.../routes/schedulePlanning.route.js` — `/dispatch-helper`, `/customer-month-schedules`

### Caveat — legacy `is_planned = 1`

**Problem:**
- Pre-model rows that meant “planned” under old coding may still be `1`.

**Cause:**
- No auto DB migration (by product choice).

**Fix / note:**
- Code `1` is **Ready to Dispatch**, not Plan.  
- Those lines do **not** appear on Today’s Dispatch Plan until re-saved as Plan (`2`) with a valid action date.

**Reflects:**
- Old half-month “planned” data missing from Plan / Today Dispatch filters until re-planned
