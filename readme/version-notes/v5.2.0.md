## 26 Oct 2026

### Documents — parent delete pe `status` soft-deactivate nahi ho raha tha

**Issue:** Module/screen se record delete hone par RMStore (ya related) entry soft/hard delete ho jati thi, lekin common `documents` table me us record ke files ka `status` `true` (active) hi rehta tha.

**Root cause:** Per-file remove (`removeDocument` / `syncPathsFromList` / `removeAllActive`) pehle se `status = false` + module file column clear karta hai. Invoice Receiving / Task delete ye call karte the. RMStore parent deletes (IPR, QC Check, Stock Adjustment, MRN) aur Machine / CL Task delete **sirf** parent row soft/hard delete karte the — `deactivateModuleDocuments` / `removeAllActive` miss.

**Before:** Parent delete → UI se record gayab · `documents.status` ab bhi `true`  
**After:** Parent delete se pehle linked documents soft-deactivate (`status = false`) + `doc_files` / `tc_file` / `rmtc_file` clear

**Reusable helper:** `deactivateModuleDocuments(MODULE, ref)` in `lib/documents/documents.helpers.js`  
- Alias: `moduleDocuments(MODULE).removeAllActive(ref)`  
- Module column + orphan active `documents` rows dono cover  
- Fail hone par log + throw (silent ignore nahi)

**Affected choke points (delete se pehle helper):**

| Module | Function |
|--------|----------|
| IPR | `softDeleteInProcessRequest` |
| QC Check | `softDeleteQcCheck`, `softDeleteQcChecksByCoilNoUids`, `softDeleteQcChecksByMrn`, `hardDeleteQcChecksByMrn` |
| Stock Adjustment (RM) | `softDeleteAdjustment` |
| MRN Portal | `hardDeleteMrnByUid` |
| Machine Master | `deleteMachines` |
| CL Task | `deleteMaster`, `deleteInstance` |

**Already correct (no change):** Invoice Receiving clear, Task chat/task delete, IPR/IR/Machine attachment sync on save, TC/RMTC replace via `upsertTcRmtcSlot`.

**Verify:**

1. IPR pe photo upload → record delete → `SELECT status FROM documents WHERE mod_type = 'rm_in_process_request' AND mod_ref = '<id>'` → sab `false`
2. MRN pe TC/RMTC → sticker cancel / MRN delete → `mod_type = 'rm_mrn_portal'` rows `status = false`
3. QC Check delete / reopen → `rm_qc_check` docs inactive
4. SA delete → `rm_stock_adjustment` TC/RMTC inactive
5. IPR se sirf ek file hata ke save → pehle jaisa `status = false` (regression)

**Known / follow-up:**

- QC UI saved doc pe sirf **Replace** allow karti hai (clear nahi) — isliye clear-without-replace path change nahi kiya
- Purane already-deleted parents ke orphan `status = true` rows ke liye one-time SQL cleanup alag se chahiye ho sakta hai
- Soft-deleted parents restore flow nahi hai; restore add ho to docs dubara activate karne ki rule decide karni hogi

**Files:** `documents.helpers.js`, `documents/index.js`, `documents/README.md`, `inProcessRequest.model.js`, `qcCheck.model.js`, `stockAdjustment.model.js` (RM), `mrn.model.js`, `machineMaster.model.js`, `clTask.model.js`

### Notifications — Web Push HTTP 403 (stale / VAPID mismatch)

Module PWA Message Logs could show **Failed** with `Received unexpected response code (HTTP 403)` even when the **in-app bell** (inbox) saved successfully. FCM/Mozilla often return **403** when the browser subscription was created under a different VAPID key (or the endpoint was revoked). Previously only **404 / 410** removed the bad row, so the same device kept failing.

| Change | Behaviour |
|--------|-----------|
| Backend | Treat **403** like stale — remove `mst_push_subscriptions` endpoint after failed send (same as 404/410) |
| Frontend | Store VAPID public-key fingerprint; if missing/mismatched, `unsubscribe` + subscribe again before saving to server |
| Login / link | `linkPushSubscriptionToUser` uses the same refresh when permission is already granted (avoids re-saving a dead endpoint) |

**Message Log meaning (unchanged):**

| Timeline step | Meaning |
|---------------|---------|
| In-app notification **Done** | Bell / inbox row saved — open from the notification bell |
| Browser push **Failed** | Tray / OS push did not reach the device |

**Deploy / verify:**

1. Restart backend; hard-refresh frontend (or reopen PWA).
2. As the affected user, allow notifications again (enable banner / site Allow).
3. Trigger a test — Message Log should move **Sent → Received** (not Failed / 403).

**Files:** `backend/.../push/webPush.service.js`, `frontend/src/common/pwa/webPushSubscribe.js` (subscribe + link paths).

### Production — Required Qty (KG) = gweight × qty + 10%

One helper for Maintain Job Card, Shortage weight, Tooling, and RM Store ERP items:

```js
// jobCard.config.js
ISSUE_QTY_EXTRA_PCT = 10

issueQtyKg(gweight, qty) =
  (gweight × qty) + (gweight × qty × ISSUE_QTY_EXTRA_PCT / 100)
```

**Example:** gweight `0.0025`, qty `369010` → base `922.525` + 10% `92.253` → **1014.778 KG**.

Change only `ISSUE_QTY_EXTRA_PCT` to raise/lower the buffer. Shown as **RM Required** / **Total Weight** in the UI.

**Files:** `jobCard.config.js`, `jobCard.controller.js`, `primeItemShortage.js`, `tooling.controller.js`, `rmstore/.../erpItems.js`.
