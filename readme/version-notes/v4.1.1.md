## A. PostgreSQL backup interval (15 minutes)

Scope: **Backend → DB backup cron**

### 1. Interval

The scheduled dump ran once per hour (`0 * * * *`). It now runs every **15 minutes** (`*/15 * * * *`).

Work hours are unchanged: **08:00–19:00** (IST). Outside that window the 15-minute job does not write a dump.

---

### 2. File names

Hourly files used `dbname_YYYY-MM-DD_HH.dump`, so a 15-minute schedule would overwrite the same file four times in one hour.

Each slot now has its own file:

| Tick | Example |
|------|---------|
| :00 | `dbname_2026-09-05_14-00.dump` |
| :15 | `dbname_2026-09-05_14-15.dump` |
| :30 | `dbname_2026-09-05_14-30.dump` |
| :45 | `dbname_2026-09-05_14-45.dump` |

Folder: `hourly/` under `DB_BACKUP_DIR`.

Cleanup still matches the previous hour-only names (`dbname_2026-09-05_14.dump`) and the older `HH-MM-SS` names, so leftover files are removed with the rolling set.

---

### 3. Retention

`hourlyKeepCount` counted **files**, not hours. Four hourly files meant **four hours**. Four 15-minute files would have meant **one hour**.

Keep count is **16** (4 slots × 4 hours) so the window stays about four hours.

| Setting                           | Value             |
|-----------------------------------|-------------------|
| `DB_BACKUP_CRON`                  | `*/15 * * * *`    |
| `DB_BACKUP_HOURLY_KEEP_COUNT`     | `16`              |
| `DB_BACKUP_HOURLY_START_HOUR`     | `8`               |
| `DB_BACKUP_HOURLY_END_HOUR`       | `19`              |

---

### 4. Weekly (unchanged)

Weekly dumps still write **once at 00:00** into `weekly/` (`dbname_Monday.dump` … `dbname_Sunday.dump`). The extra minute check (`minutes < 15`) stops the `*/15` cron from running weekly four times after midnight.

Manual `npm run backup` still skips weekly.

---

### 5. Safety (unchanged)

- Dump writes to `.tmp`, then rename
- Overlap lock skips a tick if the previous dump is still running
- Failed dump does not replace the last good file

---

### 6. Files (backup)

| File | Change |
|------|--------|
| `backend/.env` | `DB_BACKUP_CRON=*/15 * * * *`, `DB_BACKUP_HOURLY_KEEP_COUNT=16` |
| `backend/src/config/app/config.js` | Default cron `*/15 * * * *`; default keep count `16` |
| `backend/src/jobs/system/dbBackup.js` | 15-minute file name; weekly gated to the `:00` tick; cleanup regex accepts `HH-MM` |

Restart the backend once so the new cron and keep count load.

## B. Task — Chat auto-notify

Scope: **Task chat** · **Notifications settings** · **Activity log**

When a user sends a chat message on a task, the system now notifies all other assigned users (PWA and/or WhatsApp — as configured). The message is also logged in the task activity timeline.

---

### 1. Trigger

| Step  | What happens |
|-------|----------------|
| 1     | User sends a chat message on a task (`POST /api/task/tasks/:id/chat`) |
| 2     | Existing rules still apply — chat locked until target date is set (except Assigned By) |
| 3     | Message is saved to `task_chat` (unchanged) |
| 4     | Activity log entry `chat_message_sent` is written with message preview |
| 5     | Other task members get notification via enabled channels (background — does not block chat) |

---

### 2. Who gets notified

All task participants **except the sender**:

- Task creator
- Assigned-by person
- Active assignees in the assignment chain (Level-1 + sub-users)

Same people shown in the chat **Members** list.

If only one person is on the task → no notification sent (chat + log still work).

---

### 3. Channels

| Channel | Support |
|---------|---------|
| PWA (bell + tray) | Yes — via existing `sendTaskPwaPush` |
| WhatsApp Free / Paid | Yes — via existing gateway |
| Email | No — not wired for task notifications (unchanged) |

Notifications run only when the **Chat** template is **Enabled** in settings with at least one channel on.

---

### 4. New notification template — `chat_message`

| Field | Default |
|-------|---------|
| Label | Task Chat Message |
| Subject | `New message on {{task_title}}` |
| Body | Includes `{{sender_name}}`, `{{message_preview}}`, task vars |
| Enabled | **Off** (same as other templates — turn on manually) |

New template variables:

- `{{sender_name}}` — who sent the chat
- `{{message_preview}}` — first 200 chars of text, or `[N attachment(s)]`

Seeded automatically on backend start if missing (`seedTaskNotificationTemplates`).

---

### 5. Settings UI

New **Chat** tab added in:

- `/settings/notifications`
- `/task/dashboard/notifications`

Also added to **Send Message** type dropdown and **Logs** template filter.

Super Admin can enable/disable, set PWA + WhatsApp, and edit subject/body.

---

### 6. Activity log

| Item | Detail |
|------|--------|
| Action type | `chat_message_sent` |
| Detail | Message preview or attachment count |
| UI | Shows in task **Activity Log** with blue **Chat Message** badge |
| Refresh | Task detail reloads after send so log updates immediately |

Notification delivery is logged separately under **Notifications → Logs** (unchanged pipeline).

---

### 7. Deploy steps

No database migration. No new npm packages.

## C. Forwarding Note — live bill, dropdown, perms, print

Scope: **IMS → Forwarding Note** (Item-wise + Master)

---

### 1. Live merge

IMS `uid` is `acc-item-packing-qty`. Same key on many FN lines used to copy **one** live bill onto every matching row.

| Rule | Behaviour |
|------|-----------|
| Date | Live bill only if **bill date = FN date** (IMS `billdt` e.g. `03-09-2026 16:57` → day only) |
| Exclusive | One live bill → one unsaved item-wise row (lowest `fi.id`) |
| Saved DB bill | Always shown on that row (not hidden by live exclusive) |
| Color | Live follows IMS status (green etc.). **Saved (DB) = blue** |
| Master | Unique item bills rolled up |

Display only. No auto-write to `bill_no`. `BILL_SOURCE_PREFER` still `db`.

---

### 2. Dropdown (Select bill)

| Rule | Behaviour |
|------|-----------|
| Match | Super admin: customer + item. Others: customer + item + packing |
| Options | Bill no. + `Item · Pack · Qty` |
| Hidden | Bills **already attached** (saved `bill_no` on another item-wise row) |
| Save | Only **green** IMS bills |
| Info line | How the list is matched + same FN date + attached hidden |

---

### 3. Permissions

| User has | Attach (first save) | Update / Clear saved |
|----------|---------------------|----------------------|
| Special `manage_forwarding_bill` | Yes | No |
| Special + **Edit** | Yes | Yes |
| Edit only | No | No |
| Super admin | Yes | Yes |

---

### 4. Print

## D. Dashboard — widget drawer (access + width)

Scope: **IMS Dashboard** (live / read-only widgets with **Drawer** link)

---

### 1. Issue

| # | Problem |
|---|---------|
| 1 | Widget click → drawer opened but table **empty** |
| 2 | Error: **"Only super admin can perform this action"** |
| 3 | Drawer used builder API `POST /widgets/preview` (super admin only) |
| 4 | Normal users with dashboard + module access could see KPI but not drawer data |
| 5 | Drawer width felt **too wide** (~full screen) — left dashboard barely visible |

---

### 2. Solution

| # | Fix |
|---|-----|
| 1 | Drawer data loads via existing **`POST /dashboard/widgets`** with `parent_widget_id` |
| 2 | Backend reads **drawer widget config from saved dashboard** (not from client query) |
| 3 | Access checks (same as live dashboard): **dashboard access** → **widget audience** → **module (`target_page_module`)** |
| 4 | Parent widget must have `link_type = DRAWER` |
| 5 | Drawer width capped at **`55vw` / max `52rem`** — not full screen; left dashboard stays visible |

No new route. Builder preview APIs unchanged.

---

### 3. Flow

1. User clicks KPI/widget with Drawer link  
2. Frontend sends `parent_widget_id` + dashboard context (`app_key`, `page_key`, `dashboard_key`, `filters`)  
3. Backend validates access → runs drawer widget query → returns rows  
4. Drawer renders table inside `WidgetRenderer` (read-only)

---

### 4. Files

| Area | File | Change |
|------|------|--------|
| BE | `backend/src/apps/dashboard/modules/dashboard/controllers/dashboard.controller.js` | `resolveAuthorizedDrawerWidget`; drawer branch in `getDashboardWidgetsHandler` when `parent_widget_id` sent |
| FE | `frontend/src/common/dashboard-builder/services/dashboardApi.js` | `getDashboardWidgets(..., parentWidgetId)` → adds `parent_widget_id` to body |
| FE | `frontend/src/common/dashboard-builder/utils/widgetClickLink.js` | Pass `parentWidgetId` when opening drawer |
| FE | `frontend/src/common/dashboard-builder/components/DashboardBuilder.js` | Attach `appKey`, `pageKey`, `dashboardKey`, `filters` to drawer payload on open |
| FE | `frontend/src/common/dashboard-builder/components/WidgetClickDrawer.js` | Load via `getDashboardWidgets`; width `max-w-[min(55vw,52rem)]` |
